**Specification to tests.** A scoped manager maps the owning specification to single-line natural-language scenarios. A separate manager independently reviews each obligation against the list and the available fixture APIs, publishing the reviewed list and coverage assessment. It hands off one scenario per test author with a dependency on the review assignment. Mapping, review and authorship each have separate task identities and receipts. The focused source owner how/should/cointos/map/specifications/to/tests.md defines those handoffs.

**Landing.** Work travels as packets: a test-contract worker writes a behavior's tests from its contract. When they finish, CointOS runs the suite with them merged into main: every completed packet goes to an integrator before it satisfies any dependency. The integrator checks that witness inputs can represent the expected outputs and assertions match the owning contract. On cointos land, the exact reviewed candidate runs: green tests publish; executed red tests are accepted without publishing main and stay hidden from the implementer. Timeouts and invalid execution cannot authorize acceptance. When the implementer finishes, CointOS runs the hidden tests; failures return with only failing tests revealed. Existing/shared harness changes, reused command registrations or packets without new commands run their registered suite, deduplicated across packets. Distinct new packet commands remain scoped; unchanged command names cannot justify skipping assertions in changed harnesses. Submission and landing exempt only commands registered and failing on pinned main. New commands must pass; execution errors block. Submission records packet_gate counts. Comparison is by command, not individual assertions. A contradictory contract needs independently accepted correction bound explicitly, preserving the existing packet dependencies. Concurrent insertions in protected test files retain a whole block once when already present; otherwise current-side blocks precede packet blocks. Repeating review preserves committed candidates; replacements still need review. Completion, review and landing share this composition. The integrator reviews and lands code and tests together; a clean committed candidate can be submitted directly, with the worker account recorded without changing its tree; the daemon validates its receipt, tests and run ownership on a fresh checkout before landing. Commit-message wording does not authorize or refuse landing. A test passing on main and failing on the candidate returns the item with that test added to its packet; a failure main already has does not block it. Stage checks inspect worker commits and exclude commits already on main: test writers cannot change production, implementers cannot change tests, and importing landed prerequisites is allowed. Every stage needs a complete worker receipt before landing; blocked workers go directly to one recovery controller, which verifies the cause and repairs the assignment or requests independently reviewed test correction. If concurrent main changes cause a landing conflict, resolve and stage the files preserving both sides, then repeat `cointos land` with the same summary; it commits the resolution and runs the landing gate. A verified acceptance is the terminal authority for its task and queue record.

A success test must assert the promised success/output, never a failing stub's current behavior. Named-error tests must establish the phase and native provenance, not accept any error. Green tests do not establish an absent implementation. Test-contract witnesses must reach the tested boundary and assertions must remain valid after all promised implementations land. Tests enforce only what the contract says, since the implementer works from the same contract without seeing them: success and failure cases must construct the different inputs or state their outcomes require. A currently unimplemented adapter is not a permanent error contract. Rollback comparisons capture the promised unchanged state before the failing call. Test-contract tool calls carry a relies_on array of function and type names, each checked to exist somewhere on main before dispatch; an absent API sends the item to a manager unworked. `cointos metrics [--hours N]` summarizes landings, gate returns and recoveries.

Protected paths can include build harnesses such as Makefile. Test-contract workers may change them. A candidate-content mismatch supplies exact Git comparison refs: preserve main plus the submitted packet, or return defective packet changes to the worker. Reclassifying the stage does not repair altered review content.

Implementation/integration under a test policy needs an accepted test-contract dependency. Before launching an item model, the runner composes its full current accepted binding set against pinned main in a disposable checkout, outside the state lock. It executes no tests and leaves the worker checkout intact. Incompatible packets fail the assignment directly into existing recovery, with exact main/packet refs and conflicting paths, without infrastructure launch retries. Recovery requests a typed independently reviewed correct-tests replacement; acceptance switches dependent bindings atomically while preserving prior evidence and code. The final submission/landing checks still revalidate current inputs. Brief citations are not bindings. Submission refuses an empty packet; landing and incorporation require receipt test commits to match current accepted dependencies. Incorporation also requires the packet's tests already on main. A prior zero-test receipt cannot authorize a new landing, while a matching already-published verified intent retains recovery authority.

Acceptance results retain via and gate: suite counts commands, failed counts candidate failures, and red_on_main counts those also failing on prior main. via=tests means independently accepted hidden tests, not publication; via=landing means published work. CLI states that distinction and prints measured failures. Counts survive publication recovery and lost-reply replay in acceptance/receipt/queue evidence. Historical missing counts stay unknown; successful acceptance alone cannot establish a wholly green suite.

Validation bounds each command after acquiring its output lease (default five minutes) separately from the full validation including waits (default thirty minutes). CLI and MCP allow the full operation. Timeouts, killed processes or failed execution units are infrastructure errors: they cannot authorize red-packet acceptance. Repeated unchanged execution failures escalate separately from product refusals to the recovery controller. Source submission reuses product-failure evidence before validation when the complete acceptance fingerprint is unchanged; requests still advance the existing refusal bound. Execution failures rerun. Composition conflicts block directly on the first current refusal with structured main/candidate refs, packet commits and paths available through task inspection, including the recovery view. Changed inputs invalidate reuse. Final authority checks and blocked-receipt replay still apply.


Review may include the submitting run's retained scratch. For unresolved verification questions, inspect useful diagnostic sources, copy them into your own scratch and replay against the exact candidate. Check assertions and exit status: retained mutable probes are unverified.

Diagnostic shell commands must preserve the checked command's exit status before filtering output or running another command. A successful tail/tee/echo does not establish that the test passed. Run build-dependent probes only after a successful build; a failed rebuild can leave a stale executable unrelated to the changed source. Expected-failure tests require their own explicit result checks. These reports remain diagnostic; the daemon executes the exact candidate through its own acceptance gate.

Positive witnesses must satisfy the tested API's preconditions and the owning laws claimed by the test, including validators implemented later. Distinguish phase-local success from whole-pipeline validity. A permissive current builder cannot justify success for a state the final contract forbids. Review each named property's varied input and observable consequence: a hand-normalized fixture does not demonstrate normalization/deduplication, and a build failure does not prove all claimed laws. A retrospective audit must identify actual coverage elsewhere before dismissing an unexercised obligation as a mere strength concern. Mechanical acceptance remains distinct from this semantic judgment.

A counterexample that violates a promised behavior while passing its packet is a failed semantic review. Return an unaccepted packet with the original obligation, exact probe/source refs and command/result. For an already accepted packet, finish blocked for independent correct-tests recovery; returning an implementation or the old test author cannot replace its binding. Running and recording a passing wrong implementation does not prove discrimination. Do not narrow behavior into structural coverage or defer its proof until after the acceptance it must authorize. Skeleton-only contracts may legitimately promise structure. Carry unresolved findings through interruption and handoffs; an explicit authorized scope decision is required to remove a product obligation.

This gate enforces recorded correction authority, not semantic truth of a reviewer's claims.
