**Specification to tests.** A scoped manager maps the owning specification to single-line natural-language scenarios. A separate manager independently reviews each obligation against the list and the available fixture APIs, publishing the reviewed list and coverage assessment. It hands off one scenario per test author with a dependency on the review assignment. Mapping, review and authorship each have separate task identities and receipts. The focused source owner how/should/cointos/map/specifications/to/tests.md defines those handoffs.

**Landing.** Work travels as packets: a test-contract worker writes a behavior's tests from its contract. When they finish, CointOS runs the suite with the proposed tests included in the accepted product: every completed packet goes to an integrator before it satisfies any dependency. The integrator checks that witness inputs can represent the expected outputs and assertions match the owning contract. On cointos land, the exact reviewed candidate runs: green tests publish; executed red tests are accepted privately without changing the accepted product and stay hidden from the implementer. Timeouts and invalid execution cannot authorize acceptance. When the implementer finishes, CointOS runs the hidden tests. The first product-test failure records a blocked receipt and transfers the assignment to independent First Responder recovery, preserving the exact candidate, acceptance inputs, failed tests, helpers and output. The failure does not presume that production code is wrong: recovery distinguishes code defects, invalid accepted tests and missing prerequisites. A supervisor cannot bypass this handoff by revising the failed worker; only its canonical recovery owner or the user can revise it. Independently accepted corrections retain their existing authority to resume preserved work. Existing/shared harness changes, reused command registrations or packets without new commands run their registered suite, deduplicated across packets. Distinct new packet commands remain scoped; unchanged command names cannot justify skipping assertions in changed harnesses. Submission and landing exempt only commands registered and failing on the pinned accepted product. New commands must pass; execution errors block. Submission records packet_gate counts. Comparison is by command, not individual assertions. A contradictory contract needs independently accepted correction bound explicitly, preserving the existing packet dependencies. Concurrent insertions in protected test files retain a whole block once when already present; otherwise current-side blocks precede packet blocks. Repeating review preserves prepared candidates; replacements still need review. Completion, review and landing share this composition. The integrator reviews and lands code and tests together; CointOS captures the reviewed files and validates their receipt, tests and run ownership in an isolated copy before publication. Wording cannot authorize acceptance. A test passing in the accepted product and failing on the candidate returns the item with that test added to its packet; a failure the accepted product already has does not block it. Stage checks inspect authored changes independently of accepted prerequisites: test writers cannot change production, implementers cannot change tests, and importing landed prerequisites is allowed. Every stage needs a complete worker receipt before landing; blocked workers go directly to one First Responder, which verifies the cause and repairs the assignment or requests independently reviewed test correction. If the accepted product changes, call review again. CointOS prepares the files automatically. Knowledge overlaps are presented as current accepted definitions requiring ordinary knowledge upkeep before renewed review; behavioral incompatibilities must be returned with specific evidence. No conflict markers or repository repair are required. A verified acceptance is the terminal authority for its task and queue record.

A success test must assert the promised success/output, never a failing stub's current behavior. Named-error tests must establish the phase and native provenance, not accept any error. Green tests do not establish an absent implementation. Test-contract witnesses must reach the tested boundary and assertions must remain valid after all promised implementations land. Tests enforce only what the contract says, since the implementer works from the same contract without seeing them: success and failure cases must construct the different inputs or state their outcomes require. A currently unimplemented adapter is not a permanent error contract. Rollback comparisons capture the promised unchanged state before the failing call. Test-contract tool calls carry a relies_on array of function and type names, each checked to exist somewhere in the accepted product before dispatch; an absent API sends the item to a manager unworked. `cointos metrics [--hours N]` summarizes landings, gate returns and recoveries.
