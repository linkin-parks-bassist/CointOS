**Coin history.** `coin.history_messages` is the upper threshold (20) and `coin.history_trim_messages` is the discard batch (7). When conversation history reaches twenty messages, discard the oldest seven from the prompt, leaving thirteen, then append until twenty and repeat. Incoming text/captions and every accepted outgoing Telegram message count, including attention notices and explanations; captionless attachments use independent filesystem intake and do not enter chat history; internal clocks, saved-wake instructions and tool transcripts do not. Before enough history exists there may be fewer than thirteen. New active requests are never discarded. Legacy photo-only user receipts are excluded before selecting the window; captions remain conversational. Ordinary profiles retain an append-only on-disk archive and timestamps. A profile with retain_archive=false physically prunes old text using the same configured window/batch. One conversational egress archives each accepted outgoing part, including partial sends, under a file lock with chat-scoped Telegram message IDs. Mid-turn deliveries enter the next model prompt. Durable reply-to references retain the quoted message even after history rolls. Telegram update IDs make history recording idempotent on retry; current pending IDs are excluded from the historical prefix. In model context, archived media receipts use cointos-archived-attachments and pending input uses cointos-current-input with its update ID. Archive bytes retain the original content; old receipts are historical observations, not current filesystem proof.

Coin marks the selected history as a reusable native prefix. A per-user semantic prefix checkpoint survives changing round clocks, timelines and tool tails independently of the near-tail checkpoint. Growing history can restore it; batch rollover invalidates changed user prefixes but retains shared system/tool starts. Cache eviction, changed instructions/tools and rollover can still require prefill. There is no fixed twenty-four-second startup timer. The Telegram polling timeout is a maximum wait for updates, not a delay before responding to an arriving message. Cache and latency improvements require measured evidence; preserve the distinction between saved history, cache state, model generation and Telegram delivery.

Explicit user-authorized log deletion is separate from normal rollover. Stop the selected Coin service, extract only Telegram IDs/timestamps locally without displaying message contents, request eligible Telegram deletions, and remove its conversation/turn logs before restarting. Professional may also have inherited copies under state/coin. Preserve the intake cursor so old updates do not replay; deleting logs does not cancel retained tasks, reminders or standing rules. Telegram bot deletion is limited to messages younger than 48 hours; older app history requires the user's Clear History action. Successful deleteMessages batches can skip already absent IDs, so report accepted batches rather than claiming a verified count of deleted messages.

Profiles with retain_diagnostics=false, including Personal, produce no turn journal or captured model requests, expose no reply text through the dashboard, and save no inference checkpoints or tool-history token copies. Only rolling conversation context, necessary retained instructions and deliberately saved knowledge/files remain. These controls cover Coin itself; delegated Operators retain normal durable task/session storage. The context itself is still locally readable; these controls minimize transcripts rather than enforcing a filesystem sandbox.
