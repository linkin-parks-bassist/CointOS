CointOS runs local OpenCode agents through a pre-emptive GPU gateway on the user's workstation; Coin is its Telegram control. `cointos status`, `agents`, `jobs`, `task PROJECT:TASK` and `check` inspect the daemon; `stop` pauses autonomous agents and `go` resumes them. `cointos kill AGENT` terminates the run and durably holds unfinished work uncharged with its artifacts preserved. `cointos resume PROJECT:TASK` explicitly releases that hold; `go` does not. Process control never decides task failure. The source repository's knowledge tree (~/Projects/CointOS/.knowledge) is the maintained description; this answer summarises what an agent working here needs.

**Work.** The daemon alone owns scheduling records and publishes the current queues in this tree (what/is/queued.md, what/is/the/command/queue.md). Submit work with `cointos queue PROJECT NAME "BRIEF" --kind queued|urgent|command`, with `--stage skeleton|test-contract|implementation|integration` for worker items, optional `--reasoning-effort low|medium|xhigh` and optional `--generation-seconds N` / `--generation-tokens N` run budgets. A `Depends on: name, other` line in the brief names prerequisites; only daemon-accepted work satisfies them. Managers, integrators, stewards and test auditors propose as their own run; the daemon enforces who may propose what.

**Changing queued work.** A project's running manager (or the user) can hold an item with `cointos hold PROJECT:ITEM`: it will not start, and a run of it now stops without losing its branch or attempts. `cointos revise PROJECT:ITEM "COMPLETE BRIEF" --reason "WHY"` (optionally `--stage`, `--reasoning-effort`, `--generation-seconds/--generation-tokens`) replaces what the item asks for, including its `Depends on:` line; omitted stage and reasoning retain their previous values, and supplied budget fields merge with existing limits; its task restarts fresh on the new brief, keeping its branch, and a reviewed item goes back to its worker. Existing waiting integrators wait until their worker is back in review and unheld; a changed brief refreshes their assignment and conversation while preserving their branch/files and explicit admission holds. `cointos hold PROJECT:ITEM --release` lifts a hold; a manager's holds also end when its task settles. Accepted work cannot be revised; queue new work instead. If an operation you need is not described here, report it rather than reading CointOS's source.

**Every run ends with one completion receipt**, checked against its artifacts: `cointos finish --complete "EVIDENCE"` or `cointos finish --blocked "BLOCKER"`. Workers commit their work and `.work-report.md` (one `Status: done` or `Status: blocked`) on their branch, then submit that exact commit for review with the matching receipt. Managers, gardeners, tree auditors and project operators land with `cointos merge` before completing. An integrator reviews with `cointos review`, then its receipt is a verified `cointos land "SUMMARY"`, `cointos incorporate PROJECT:ITEM --commit MAIN --worker-commit WORKER`, or `cointos return "NOTES"`. A successful terminal command prints and flushes its receipt, then the daemon stops that exact managed run. Final messages, finish markers and process exit never complete a task; a run ending without a receipt is retried a bounded number of times.

**Landing.** The daemon lands only the exact reviewed candidate, on a fresh checkout: implementation commits cannot change protected tests, and every accepted test contract covering changed code must pass; unrelated red tests may remain. A failed implementation returns to its worker with the failure. A verified acceptance is the terminal authority for its task and queue record.

Test-contract witnesses must reach the tested boundary and assertions must remain valid after all promised implementations land. A currently unimplemented adapter is not a permanent error contract. Rollback comparisons capture the promised unchanged state before the failing call.

**Blocked work.** An integrator-confirmed worker blocker or exhausted worker retries automatically dispatch one bounded manager pass with the original assignment and receipt evidence. Recovery managers use their own configured reasoning and default run budget rather than inheriting worker overrides. Report wording does not control routing. The manager may hold/revise a mistaken brief or replace oversized work with `cointos replace CHILD...`; correcting a brief does not accept the failed work. An unresolved or exhausted manager escalates to the user without another automatic pass for the unchanged failure. An integrator verifying that an assignment is impossible must finish blocked with the evidence rather than return the unchanged assignment to its worker.

**Budgets and reasoning.** Each run has a pinned generation budget (defaults 1800 generation seconds or 36000 generated tokens; waits, prefill and tools are free), stated at the end of its launch message with its per-reply reasoning limit. Worker items without a branch artifact by 600 seconds or 12000 tokens restart early. Exhaustion restarts a run fresh, at most twice, from a bounded evidence packet; `cointos budget PROJECT:TASK` changes only waiting work, `cointos reasoning PROJECT:TASK LEVEL` changes effort from the next reply.

**Launch failures.** A run becomes assignment-engaged only when its first model request reaches the gateway. A process that exits earlier is refunded and counted separately; after two consecutive launch failures its waiting task is durably held and the user is alerted instead of spending assignment attempts or respawning forever.

**Caches and retained work.** Disposable snapshots are removed when their conversation can no longer resume, including workers accepted after their own run ended. A terminal task's surviving run keeps its cache until release. Startup and periodic reconciliation clean unreachable owners; interrupted cache transfers become cold. This does not delete conversation history or retained branch artifacts.

**Continuity and restart.** A managed task pins the complete system/developer prefix from its first model request, and the gateway journals a digest of each request's system prompt without retaining the prompt. Relaunching the same OpenCode session after an interruption under three hours sends only `Continue.` because OpenCode rejects an empty invocation; a longer gap gets one concise reorientation. `cointos restart` stops new agent spawning but lets existing conversations issue continuation thoughts and receipts until a quiet request boundary, then replaces only the daemon. Full shutdown attempts model-context saving, disk snapshot persistence and final ledger saving independently, so one failed step does not suppress the others.

For configuration-compatible source, guidance or daemon-policy changes, `scripts/install --live` lets admitted thoughts finish and holds new requests at the admission gate without consuming client retries. Cancellation admits those requests; shutdown returns a retryable refusal. It replaces the installed copy and restarts only cointosd around surviving agent units. Reasoning, recovery, scheduling and spawning policy may change this way. It refuses changes to the gateway endpoint, backend or loaded-model identity/topology; those require a paused full installation.
The drain cancels without stopping anything after 60 seconds by default; `--wait-seconds N` changes the bound. If failure occurs after cointosd stops, installer cleanup starts it again. Coin keeps its imported code and startup settings through live installation; changes to those require a separate Coin-only restart after its conversation work is quiet.

**Task history.** The dashboard's Clear task history control removes only unreferenced terminal task and queue records. It retains evidence, sessions and branch metadata for the unfinished queue frontier and its transitive prerequisites, recovery work and workers of waiting integrators. Telegram conversation history and Git/OpenCode artifacts are separate.

**Other controls.** `cointos supersede PROJECT:FAILED REPLACEMENT... --reason EVIDENCE` replaces failed prerequisites without accepting them; `cointos clear-review PROJECT:ITEM --reason EVIDENCE` withdraws obsolete rejection feedback from waiting work; `cointos attention "MESSAGE"` lets a steward or test auditor reach the user through Coin; `cointos agent run NAME "BRIEF"` starts one bounded operator with explicit standard/control/network abilities. `cointos project list|add|new|set|remove` manages enrollment in config/projects.json, which upgrades preserve. New repositories include orientation, spec, plan and known-defects leaves plus a default test policy; inspect project list for its manifest, protected paths and non-code paths. Imported repositories need a configured test policy before workers can land; production changes need accepted coverage. Registry changes are saved before taking effect; a failed write leaves enrollment unchanged. Worktrees live under ~/Projects/.worktrees/<project>/<task> on work/<task> branches; runtime queues are read-only to agents; the owner's private directories (listed in ~/.config/cointos/private-paths) are never accessible.
