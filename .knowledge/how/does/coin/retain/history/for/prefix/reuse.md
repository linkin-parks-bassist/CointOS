Coin uses batched conversation history: history_messages=20 is the upper threshold and history_trim_messages=7 the discard batch. Grow to twenty user/assistant messages, remove the oldest seven to thirteen, then repeat every seven. Before the first threshold there may be fewer than thirteen. Current conversational requests are never discarded; tools, clocks and internal saved-wake instructions do not count. Delivered notifications and every accepted outgoing Telegram part do count, including parts preceding a later send failure. Captionless attachments now use independent filesystem intake. Legacy photo-only user receipts are excluded before window selection while their archive bytes remain intact; captions remain conversational. This prevents old photo uploads contaminating unrelated new requests.

One conversational egress retains delivered text/timestamps under a file lock, with chat-scoped Telegram delivery IDs. The delivery observer and model replies share it; notices arriving during a turn enter its next prompt. Unterminated final records are discarded before selection; malformed selected complete records refuse reading. Telegram update IDs make user recording idempotent and preserve the original timestamp on retry; identical text with another ID stays distinct. Current pending IDs are excluded before selecting history so retries preserve the same prefix. Legacy records without IDs cannot retroactively prove duplicates. Intake also persists Telegram reply-to message ID, text, time and bot provenance; quoted context remains available after rollover. Outstanding delivered-notice evidence and pending explanation turns supply explicit context beyond the rolling window. A response is interpreted against the actual delivered question, checked against current task state, then acted on through scoped controls with verified results.

Captioned historical attachment metadata is presented as cointos-archived-attachments, while current pending input uses cointos-current-input with its update ID. These labels change model context only. Old presence/path metadata is historical evidence, not current filesystem proof. Structural distinctions cannot ensure model compliance: native probes recognized archive identity but still made unsupported claims. Source tests exercise retries, rollover and legacy-photo exclusion.

At turn start cache_prefix_messages marks system plus selected history. The gateway compares native renders to establish the token boundary. A per-user Coin prefix snapshot survives volatile clock/timeline/tool tails independently of near-tail checkpoints. Longer compatible prefixes supersede older ones; rollover discards divergent user states. Shared system/tool boundaries stop before the first message role header, using both user-first and assistant-first renders because odd trims can start with either. Eviction or changed instructions/tools can require prefill.

Tool rounds retain their transcript in memory; later turns rebuild from archived conversational text. Current-input guidance, clocks, timelines, retained requests and the standing photo destination remain after the reusable prefix. The route refreshes each round independently of rolling history. The unfinished-request and attachment owners define those separate mechanisms.
