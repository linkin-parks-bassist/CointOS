After a verifier runner closes successfully, `ecosystem.executor._finalize_run_finished` calls `ecosystem.verification.finalize(verifier)`. A failed verifier with verified physical close is also finalized by ordinary execution or dead-owner replay. Finalization serializes target updates with `state/verification-finalize.lock`, reads the target and verdict artifact, snapshots result recipients, then writes the target as `completed` only when both the verifier runner succeeded and the verdict is valid and accepted, or `rejected` otherwise, recording verifier ID, summary, and verdict before auditing. Repeating finalization for the same already-terminal target returns its existing record; another terminal state is not overwritten. `cli.request_task_cancellation` takes the same verification lock while choosing and publishing cancellation, preventing a cancellation/finalization write race. The executor queues the target result notification, with periodic outbox repair after a crash.

The installed verifier prompt and `read_verdict` require a nonblank summary and `claims`, `evidence`, and `checks` lists containing only nonblank strings. `accepted: true` additionally requires at least one item in each list. An evidence-insufficient rejection may have empty lists. Missing, unreadable, invalid-JSON, non-object, or schema-invalid verdicts return a rejected reason instead of raising on shape. These are format and evidence-presence checks, not proof that the verifier's observations are true or sufficient; the independent verifier owns that judgment. A failed verifier runner cannot make its target successful: an accepted artifact is retained at its original path, while the target records an effective rejected verdict and a runner-failure summary. `finalize` refuses nonterminal verifier states such as `reconciliation_required`; the executor does not queue a target notification from that state.
