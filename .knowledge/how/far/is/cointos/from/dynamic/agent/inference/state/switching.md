CointOS already accepts durable logical agents independent of GPU execution slots, no context shrinkage from agent count, shared immutable weights, and compatible inference-state switching across GPU/RAM/disk without full prompt replay. See `what/is/intended/agent_scheduling.md`. This is accepted post-MVP intent, not implemented switching. Current plan remains capacity wrapper integration, then separately authorized activation.

Read-only observations on 2026-09-14: Lemonade 11.9.0 health and backend `/props` identify Qwen3.8-27B-GGUF, Vulkan llama-server b10723-010be9683, `--ctx-size 131072 --parallel 1`, per-request 131072, reported model maximum 262144, no explicit unified-cache or slot-save-path flags. The backend was actively streaming; no requests for inference, cache mutation, or reconfiguration were made. Installed binary help supports unified KV, per-slot cap, RAM caching, idle-slot caching and disk slot-save-path. These are capabilities advertised, not qualification of this model's persistence.

Current `ecosystem/context_layout.py` already distinguishes fixed and shared layouts. `ecosystem/opencode_capacity.py` checks the observed per-sequence ceiling and applies pool/slot division only to fixed layout. Thus equal division is not universal project intent. No inference-state residency manager or native context-switch implementation was found in the inspected ecosystem code; generic job checkpoints do not establish KV/sampler persistence.

Upstream building blocks (checked 2026-09-14): llama-server exposes unified KV pooling, per-slot context caps, RAM prompt caching and slot cache save/restore. Lemonade documents forwarding `/v1/slots/{id}?action=save|restore|erase`, requiring backend `--slot-save-path`. Unified KV is a finite preallocated pool, not arbitrary simultaneous full contexts or automatic durable OS-style paging. A shared pool can support unequal actual context occupancy; retaining a per-agent ceiling does not guarantee simultaneous full occupancy fits.

llama.cpp's public C API separates model/context objects and exposes full-context and sequence state serialization, as well as sampler cloning/copying. A lower-level adapter could share a loaded model and manage contexts/state itself. Full agent recovery also requires exact token history, model/tokenizer/template/config identity, recurrent/SWA state, sampling/RNG/grammar state, generation cursor, tool-call/results and client state. Mid-generation bit-identical continuation is a stronger promise than preserving a conversation or restoring prompt cache, especially across builds/devices/batching changes. Checkpoints should initially occur at completed inference/tool boundaries; stronger preemption requires separate qualification.

Open upstream issue https://github.com/ggml-org/llama.cpp/issues/25913 reports successful-looking slot restore but zero prompt reuse on hybrid/recurrent Qwen; linked proposed fix https://github.com/ggml-org/llama.cpp/pull/26004 preserves recurrent checkpoints, and includes Qwen3.8 user reports. This is a qualification risk, not a reproduced failure on David's installed binary. HTTP success/token counts alone cannot certify no-replay restoration.

vLLM now documents CPU KV offload plus filesystem secondary tiers, https://docs.vllm.ai/en/latest/features/kv_offloading_usage/. This is a closer candidate for dynamically allocated/tiered cache serving, but prefix-cache offload is not by itself complete durable agent checkpointing. Its documented accelerator support is CUDA/ROCm/XPU, not Vulkan. Model, quantization, hardware and recurrent-state support must be checked before migration.

Hosted OpenAI APIs support separate conversations and full per-request model contexts (subject to rate limits), with Conversations/Responses durable items and response chaining. They do not expose weight residency, raw KV export/import or arbitrary exact decoder checkpoint recovery. Prompt caching is provider-managed, finite-retention and routing dependent; it is not a user-owned durable snapshot. Standard OpenAI-compatible chat APIs likewise need a backend-specific extension for native state management.

Recommended investigation, not an approved replacement plan: qualify two full-ceiling requests on the exact current build with a shared pool; benchmark actual KV/recurrent memory and service throughput; then test A-save/erase/B-run/A-restore and backend-restart restoration, verifying actual prefix reuse and state integrity. Implement agent-owned atomic/versioned snapshots and bounded admission/eviction only after qualification. Prefer whole-agent residency switching at safe boundaries before disk paging during every decode step. Retain immutable weights while dormant agents reside on disk; bound active work by measured memory/service, not a reduced context allowance.
