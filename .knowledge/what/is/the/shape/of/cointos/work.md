The user's direction of 2026-09-27 is **everything small, pipelined, hardware-like**. Local models have useful flexibility within one well-bounded concern; CointOS must not rely on that flexibility across a large assignment. Agents are execution units, work flows through their stages, and abstraction keeps the next level small too.

**Universal pipeline invariant.** Every assignment is one bounded stage: it consumes a bounded artifact or question and produces a checkable artifact, an explicit boundary and the next handoff. There is no monolithic level above the worker pipeline. Decomposition is a pipeline of decomposition stages; implementation, testing, verification, integration, maintenance and recomposition follow the same rule. A stage may expose another stage of its own kind. Managers record the unexpanded frontier in the project plan, queue only concrete children, merge their bounded planning change and finish with `cointos finish --complete "evidence"` or `--blocked "reason"`; queued children continue independently. Forced continuation managers are retired. Integrators may instigate one same-project managerial follow-up exposed by acceptance, and periodic system-wide scouts rediscover valuable loose ends without polling chains.

**Current sizing calibration.** The initial live pipeline showed that 10–20 minutes still permitted assignments with too many hard subproblems. The current Qwen3.8 calibration on this hardware is about 8–15 minutes of substantive work, aiming near 10, excluding prefill and lane waits. Reaching 15 minutes is a strong pre-dispatch signal to split scope; it is a pre-dispatch sizing target, separate from the runtime generation budget. The default authorized run budget is 1,800 generation seconds or 36,000 generated tokens, excluding waits/prefill/tools, with up to two fresh-session retries preserving artifacts before assignment failure. Failed worker items then receive one bounded manager pass; unresolved or exhausted managers escalate for intervention. Recalibrate when the model or hardware changes. Future models have no assumed capability or release date here.

**Task budget metadata.** Tasks carry daemon-owned budget metadata (`generation_seconds`, `generation_tokens`). Defaults remain 1,800 generation seconds and 36,000 generated tokens including reasoning; omitted proposal fields inherit defaults, and effective limits are pinned when a scheduler task is created. A recovery manager is a separate assignment: it receives configured manager reasoning and default run limits, not the failed worker record's overrides. Explicit overrides supplied for the recovery task itself still win. Directly queued worker items and manager commands retain their own record metadata. Managers can supply cointos queue --generation-seconds N --generation-tokens N (POST /api/queue budget object). cointos budget PROJECT:TASK with either flag (POST /api/budget {task,budget}) changes only waiting/undispatched work, validates before mutation and preserves the other limit. Active runs cannot change budgets underneath themselves. Every new or resumed run's launch message ends with an FYI stating its limits, accounting, artifact-preserving exhaustion behavior and exact uninterrupted-thought cap, with an instruction to decide succinctly before acting. Adoption preserves current conversations/counters without injecting a new message. Task overrides need no restart; changing configured defaults still requires daemon replacement. Fresh-retry counts remain daemon configuration, not agent-controlled budget metadata. This larger ceiling applies after useful work exists: worker items must leave a dirty or committed branch artifact by 600 generation seconds or 12,000 tokens or recover early. Fresh recovery carries a 6,000-character maximum packet of recent outward text, completed tool evidence, Git state and counters; it excludes hidden reasoning. Agents act after evidence settles a choice rather than narrating plans or reopening it. This prompt guidance is advisory; forced closure of each uninterrupted reasoning block is the mechanical backstop.

**Separation of concerns.** Product briefs state desired software behavior and acceptance. Workflow and model-specific task sizing live in CointOS policy, role prompts and orchestration. Do not insert them into a product brief to coach an infrastructure test. Derived work items carry the concrete contracts that the manager determines; the submitted brief does not prescribe decomposition. Evaluate the infrastructure through ordinary intake without manually supplying its intermediate work.

**Construction pipeline.** Plan new software as an assembly graph, then advance only its next small frontier. Begin with small skeleton tasks that establish a few related data structures, signatures, ownership/error contracts, stubs and build seams without implementing the algorithms. For each function or similarly small behavior, land a focused test-contract task before its implementation task. Test-writing and implementation stay separate on purpose: the test writer encodes intent without implementation bias and with less to hold in context, and the implementer iterates against frozen tests. The test target must compile and run; before implementation its named assertions may fail at deliberate unimplemented behavior. Discovery may include those same expected red checks; requiring that discovery to be simultaneously green is contradictory. Existing completed behavior must not regress, and compile/harness/unrelated failures are not deliberate stub failures. The dependent implementation task is judged by what it changed: covering checks green on main stay green, and a covering check already red on main must lose a failure main reports, while unrelated or later items' reds may remain, even in the same test binary. Test files cannot change in an implementation commit. Bounded integration tasks then join a few already-tested pieces and test their shared boundary, building upward through pre-planned layers until the full system is assembled. Independent chains may run in parallel after their shared skeleton lands.

**Enforced test contracts (installed).** Queue records for worker items and worker tasks carry a validated construction stage (skeleton, test-contract, implementation or integration; implementation when omitted on creation), plus optional reasoning_effort; manager commands carry no stage. Brief-only revision retains the existing stage, effort and budget limits; explicit budget fields merge with existing limits. `how/to/revise/queued/cointos/work.md` owns the revision procedure. The global configured default is low; test-contract workers, integrations reviewing a test-contract worker and managers default medium. New integrations select the configured review default from their linked worker's stage without inheriting the worker's explicit effort/budget overrides; existing tasks retain their pinned settings. Explicit daemon-owned task overrides still win. The user's policy is to front-load effort into adversarial tests, leaving implementers and implementation reviewers a bounded implementation/sanity-check role. A new test-contract review checks every assertion, including those hidden behind the first deliberate red, for mutually consistent outcomes and properly constructed failure state. cointos reasoning PROJECT:TASK LEVEL changes future replies without altering a thought already in flight; a changed template prefix may require rereading context. Effort is request metadata, not another loaded model. CointOS mechanically closes uninterrupted reasoning at low 256, medium 384 or xhigh 1,024 tokens, then lets the same reply answer or call a tool. There is no lifetime reasoning penalty: tool calls are treated as forward motion.

Test writers must be adversarial toward the implementer: cover plausible shortcuts, boundary cases, invalid inputs and state transitions against the actual specification. Build valid witnesses through owner APIs and use malformed inputs only when the tested boundary promises to reject them. Check that construction reaches the API being tested. Frozen assertions must remain valid after all promised implementations land; a currently unimplemented adapter is not a permanent error contract. Rollback checks capture the state promised unchanged before the failing call and compare afterward. An absent valid failure witness is a contract mismatch to report, not a reason to invent a constructor or weaken assertions. Managers check these premises before queueing; integrators check them at acceptance and retrospective auditors check them in their selected landing. Test writers register a JSON list in the project's configured `test_policy.manifest` (normally `tests/contracts.json`). Each entry has exactly covers (nonempty repository-relative targets) and command (nonempty argv array). Example: {"covers":["todo/store.py::load"],"command":["python3","-m","unittest","tests.test_store.TestLoad"]}. Every test's direct and indirect code dependencies must be declared. Reviewers verify that mapping and the adequacy of assertions; CointOS cannot infer omitted semantic dependencies.

**Mechanical test-contract gates (installed).** Briefs that cite APIs which do not exist and red claims nobody checked were the costliest test-contract failures, so both are checked by the daemon rather than models. (1) Brief feasibility: `queues.contents` refuses a test-contract brief without a `Relies on: path::symbol, ...` line (path alone means the file must exist). When the item becomes ready, `spawner.feasible` checks every entry against the project's main HEAD (file present; symbol present as an identifier). An absent entry marks the record blocked with a `Dispatch check:` report and routes it to the one automatic manager pass without creating a worker; it logs `brief infeasible`. Records without the line (older briefs) are not checked. (2) Red gate: after the usual test-contract checks, `contracts.red_gate` reads the submitted worker commit's `.work-report.md`. It requires `Expected red: COMMAND => OUTPUT LITERAL` lines (or `Expected red: none`) outside fenced code. It runs every accepted contract command from main plus each declared red command on the exact candidate. Each declared red must exit nonzero and print its literal (a file:line or assertion text pins the failure point and excludes compile errors). Any other accepted command that is red on the candidate is rerun on main; green on main means a regression. A declared red may sit in an existing green target, as appending a staged section to one test binary does. A failure logs `landing gate rejected` and returns the item to its worker, exactly as for implementation; success records the gate's counts as `gate` on the `verified landing` event. All checks share one `timeouts.command_seconds` deadline, and main is consulted only for candidate-red commands. `how/to/monitor/cointos/pipeline/gates.md` owns how to judge their effect.

For implementation landings, `cointos/contracts.py` audits worker commits after its pinned base excluding already accepted main history: protected test/harness paths cannot be added, edited, deleted or renamed, even temporarily then reverted. The final integrator candidate must also preserve main's protected files and manifest. Added or changed production targets require accepted coverage from main's manifest. Python top-level functions and classes use AST comparison. Named imports are tracked through loaded names in both versions, and changes propagate transitively through same-file references. A private helper may inherit coverage from its public callers; all affected callers need contracts, and explicitly registered helper checks still run. Unreferenced helpers need their own coverage. Executable module changes, wildcard/future imports, unused changed imports, module-level consumers or unsupported syntax conservatively select all registered contracts for that file. This is static name-based selection, not proof of runtime dependency completeness: dynamic references, cross-file dependencies and import side effects still require reviewer-declared coverage. Other languages use file targets. Class-method-only mappings are not supported: use the class or file. Uncovered code fails closed; all matching registered commands run.

`contracts.implementation_gate` then judges the selected commands comparatively, because file-level coverage and one shared test binary make "must pass" blame an implementation for later items' unwritten behavior. It runs them on the exact candidate; if all pass, the implementation lands. Otherwise each is also run on main. A command green on main and red on the candidate is a regression. Among commands red on main, at least one must pass on the candidate or lose a failure that main reports: failures are identified by unittest/pytest test ids when the output names them (`FAIL:`/`ERROR:` lines, `FAILED path::test`), else by `file:line` source locations as assertion aborts print them. Failing the same test or assertion differently is not progress. This needs no declaration from implementers. Assertions behind an aborting failure stay unobserved, so regressions hidden there remain a reviewer concern. Verified on Pigen's stuck `impl-boundary` commit 617b933 against its base: one red covering check, one fixed.

The daemon's /api/land (`cointos/landing.py`) checks a clean exact candidate in a fresh detached worktree, under a bounded command timeout and outside the ledger lock. Before anything runs it requires the integration's current run and the worker branch at exactly the commit its completion receipt submitted. Each check runs in a transient systemd unit capped at memory.agent_limit_gb (currently 8 GiB), with no swap and whole-unit cleanup; this protects the host from tests launched by the daemon. A live isolated check exceeded a deliberately small 128 MiB cap and only that disposable process was killed. GNOME reports such cgroup-local OOM kills with a generic device-memory warning; inspect the kernel's constraint and unit before treating that notification as host exhaustion. A failed implementation or test-contract check automatically sends the task back to its worker with the candidate SHA and failure details, retaining its branch/session; main and dependencies remain unchanged, and the return is the integrator's receipt. Tracked changes made by tests are rejected. It checks run ownership and worker/candidate/main refs again before fast-forwarding main and settling the worker and its integration. A persisted `landing` record lets a retry settle a landing interrupted after its fast-forward; a commit that reached main without it is refused, and there is no separate accept path. The acceptance is the terminal lifecycle authority: it marks both task and queue state done and clears provisional blocker/decomposition data. Queue records are re-projected from settled tasks every tick, and successful land/incorporate API calls republish the derived queue projection. Concurrent-main conflicts leave main and task acceptance unchanged. An integrator resolves/stages the conflicting files preserving both sides and repeats `cointos land` with the same summary; the command commits the resolution and runs the same exact-candidate gate, without a manual merge commit or alternate completion command. Duplicate validation is rejected, draining waits for active landings, and an agent waiting on its bounded daemon validation is exempt from event-silence recovery.

Implementer edit-tool permissions deny configured protected paths. Shell access and Git remain same-user capabilities: this is an enforced CointOS landing policy, not an OS sandbox against a hostile agent using raw Git or modifying the runtime. Stage correctness, protected-path completeness and coverage mappings remain review responsibilities. Missing/faulty tests require a separate test-contract correction; integrators cannot repair them inside an implementation landing. Skeletons retain their distinct reviewed acceptance. Integration preserves existing protected tests and accepted contract entries, runs prior accepted checks for carried production changes, and executes newly registered contract commands. The explicit incorporate API can settle implementation already on main only with pinned main/worker commits (the worker commit must be its receipt's), structural matching of submitted changes and supporting bindings, and isolated accepted checks. Documentation and unrelated new definitions do not require duplicate implementation; semantic rewrites still require integrator judgment. supersede repairs failed prerequisite edges without pretending that the failed task was accepted.

**Concern pipelines.** Break work by interface and responsibility, not a few large features. A parser may separate lexical recognition, value construction and serialization; the precise stages depend on its contract. Each item gives one outcome, exclusions, inputs/outputs, error and ownership rules, affected area, dependencies and an executable check. It contains one hard algorithm or edge-case family. Each manager run advances one abstraction boundary and elaborates only the next one to three concerns, retaining an unexpanded frontier in the project plan. Queue records remember which task proposed them (`proposed_by`). Queued children continue without a dependency-bound continuation manager. Scope-completion evidence still requires model/reviewer judgment; the daemon does not infer product completeness from plan prose. Workers independently reject oversized or contradictory assignments as blocked with concrete evidence. An integrator verifies a blocked report and finishes blocked when the assignment needs managerial correction instead of returning the same impossible brief. The daemon automatically routes failed worker items, exhausted worker retries and briefs failing the dispatch check through one bounded manager pass with assignment and receipt evidence, independent of report phrases. The manager may revise a false brief or replace the item with smaller children. A completed revision does not accept failed work; a blocked or exhausted manager disables another automatic pass for the unchanged failure and alerts the user. All roles compute with code/tools rather than extended prose arithmetic.

**Reverse review and recomposition.** Workers report the boundary they expose and assume, checks and unresolved mismatches; the owning interface leaf states the current contract. The integrator checks one item's boundary against the actual change and neighbors. A manager command asking for a survey or coherence review compares a small set of neighboring contracts at one common abstraction level and records that layer's contract or queues one bounded coherence check. Further recomposition occurs through later bounded commands. In addition, the global retrospective test auditor samples recent accepted product work, compares its tests with the owning specification, runs bounded relevant suites, and queues at most one manager command for a concrete semantic enforcement gap. It is deliberately post-work: the system seeks eventual correction rather than requiring every landing to be perfect.

**Small gardeners.** Every registered project's knowledge tree and each explicitly configured CointOS-owned tree participates automatically. The spawner (`spawner.tree_work`) chooses up to garden.leaves_per_pass leaves (configured 3): random for routine passes, brown then yellow for health repairs. A gardener verifies only that batch plus necessary neighboring evidence, lands corrections and submits its receipt, whose validator requires a landed branch and a clean worktree. Selected leaves still non-green on main are recorded in the receipt and reported through an alert; the bounded pass ends instead of retrying until the whole tree is green. This does not validate unresolved leaves. An unchanged health set is retried only at the routine interval. Separate tree-audit tasks examine one structural concern across representative owners (duplicates, log-shaped answers, stale routes or contradictory abstraction levels). Both kinds share per-tree exclusion. Broad conceptual coverage is not permission for an exhaustive fact audit.

Role prompts, queue validation, landing contracts and runtime budgets implement these bounds. Mechanism coverage is green; live task-quality and sustained-flow acceptance remain in `what/is/the/plan.md`. OpenCode V2 migration is deferred.
