The user's direction of 2026-09-27 is **everything small, pipelined, hardware-like**. Local models have useful flexibility within one well-bounded concern; CointOS must not rely on that flexibility across a large assignment. Agents are execution units, work flows through their stages, and abstraction keeps the next level small too.

**Universal pipeline invariant.** Every assignment is one bounded stage: it consumes a bounded artifact or question and produces a checkable artifact, an explicit boundary and the next handoff. There is no monolithic level above the worker pipeline. Decomposition is a pipeline of decomposition stages; implementation, testing, verification, integration, maintenance and recomposition follow the same rule. A stage may expose another stage of its own kind. Managers record the unexpanded frontier in the project plan, queue only concrete children, merge their bounded planning change and finish with `cointos finish --complete "evidence"` or `--blocked "reason"`; queued children continue independently. Integrators may instigate one same-project managerial follow-up exposed by acceptance, and periodic system-wide scouts rediscover valuable loose ends without polling chains. When work has no route through the pipeline, any non-worker run may start an operator for it (`what/are/the/cointos/roles.md`).

**Current sizing calibration.** Managers size worker items for about 5 minutes of useful Qwen3.8 work on this hardware, excluding prefill and lane waits, and check each against the pre-dispatch tests in `roles/manager.md` (one sentence without "and", one function or contiguous test section, named reading, its own test packet, no open design decision); anything failing them gets another manager stage first. Other stages keep the 8–15 minute target. Exhausting a run's budget ends the run, never the assignment (`lifecycle.retry_fresh`): any task, worker items included, continues in up to `recovery.fresh_retries` fresh runs from its branch/files and recovery packet. Each first submits work already complete or, when the rest will not fit, reports blocked with what remains (how oversized items reach a manager); only it can submit what the previous run finished.

**Task budget metadata.** Tasks carry daemon-owned budget metadata (`generation_seconds`, `generation_tokens`). Defaults are `recovery.generation_seconds` and `recovery.generation_tokens` in `config/cointos.json`; prompts, guides and leaves name the settings rather than repeat their values. Omitted proposal fields inherit defaults, and effective limits are pinned when a scheduler task is created. A run's spend (`schema.spent`) is what it generated plus the budgets it granted to operators it started. Once a run spends `recovery.warning_fraction` of either limit, `recovery.warn` sends its session one message to commit now and finish, complete or (if the rest will not fit another run) blocked with what remains; it logs `budget warning`. A recovery manager gets configured manager reasoning and default limits, never the failed worker's overrides, though overrides set on the recovery task itself win. Directly queued worker items and manager commands retain their own record metadata. Managers can supply cointos queue --generation-seconds N --generation-tokens N. cointos budget PROJECT:TASK with either flag changes only waiting/undispatched work, validates before mutation and preserves the other limit. Active runs cannot change budgets underneath themselves. Every new or resumed run's launch message ends with an FYI stating its limits, the warning, accounting, artifact-preserving exhaustion behavior and exact uninterrupted-thought cap. Task overrides need no restart; changing configured defaults requires daemon replacement. The budget is the only per-run limit. Recovery carries a `recovery.handoff_chars` packet of recent outward text, completed tool evidence, Git state and counters; it excludes hidden reasoning.

**Separation of concerns.** Product briefs state desired software behavior and acceptance. Workflow and model-specific task sizing live in CointOS policy, role prompts and orchestration. Do not insert them into a product brief to coach an infrastructure test. Derived work items carry the concrete contracts that the manager determines; the submitted brief does not prescribe decomposition. Evaluate the infrastructure through ordinary intake without manually supplying its intermediate work.

**Construction pipeline.** Plan new software as an assembly graph, then advance only its next small frontier. Begin with small skeleton tasks that establish a few related data structures, signatures, ownership/error contracts, stubs and build seams without implementing the algorithms; they fix the names both the test writer and implementer rely on. Then, for each function or similarly small behavior, the user's packet rule (2026-10-06): code travels with its tests. The manager queues a test-contract item whose brief is the behavior's contract, and an implementation item with the same contract that depends on it. Separate workers write the tests and the code from that contract without seeing each other's work: the test writer encodes intent without implementation bias, and the implementer cannot code to the tests. While the tests fail on main they form a packet that is accepted without landing and stays hidden; when the implementer finishes, its packet runs and failures go straight back with only those tests revealed. The integrator lands code and tests together after the full suite passes, so main holds only passing tests. Tests already passing on main have nothing to wait for: they are reviewed and land at once. Bounded integration tasks then join a few already-tested pieces and test their shared boundary, building upward through pre-planned layers until the full system is assembled. Independent chains may run in parallel after their shared skeleton lands.

**Enforced construction stages (installed).** Queue records for worker items and worker tasks carry a validated construction stage (skeleton, test-contract, implementation or integration; implementation when omitted on creation), plus optional reasoning_effort; manager commands carry no stage. Brief-only revision retains the existing stage, effort and budget limits; explicit budget fields merge with existing limits. `how/to/revise/queued/cointos/work.md` owns the revision procedure. Reasoning defaults come from `reasoning` in the configuration (test-contract workers and managers have their own entries); integrations use their role default without inheriting the worker's explicit effort/budget overrides. Existing tasks retain their pinned settings, and explicit daemon-owned task overrides still win. The user's policy is to front-load effort into adversarial tests, leaving implementers and reviewers a bounded implementation/sanity-check role. cointos reasoning PROJECT:TASK LEVEL changes future replies without altering a thought already in flight; a changed template prefix may require rereading context. CointOS mechanically closes each uninterrupted reasoning block at its effort's `reasoning.budgets` entry, then lets the same reply answer or call a tool. There is no lifetime reasoning penalty: tool calls are treated as forward motion.

Test writers must be adversarial toward the implementer: cover plausible shortcuts, boundary cases, invalid inputs and state transitions against the actual specification, asserting only what the contract says. Build valid witnesses through owner APIs and use malformed inputs only when the tested boundary promises to reject them. Check that construction reaches the API being tested. A currently unimplemented adapter is not a permanent error contract. Rollback checks capture the state promised unchanged before the failing call and compare afterward. An absent valid failure witness is a contract mismatch to report, not a reason to invent a constructor or weaken assertions. Test writers register each runnable command in the project's configured `test_policy.manifest` (normally `tests/contracts.json`), a JSON list whose entries have exactly covers (nonempty repository-relative targets, descriptive) and command (nonempty argv array running only that packet's tests). The full suite is every registered command.

**Brief feasibility (installed).** `queues.contents` refuses a test-contract brief without a `Relies on: name, ...` line of function and type names. When the item becomes ready, `spawner.dispatch` creates its task and checks that each name occurs as a whole word somewhere in main's tracked tree (`git grep -w`); a `path::name` citation is accepted with its path ignored, and an entry naming a file must exist. An absent entry fails the task before any run, with a `Dispatch check:` note, so its record goes to the one automatic manager pass like any failed item; it logs `brief infeasible`. `how/to/monitor/cointos/pipeline/gates.md` owns how to judge the checks' effect.

**Test packets (installed).** A test-contract completion requires a clean branch and valid manifest. `contracts.stage_history` rejects production edits in task commits after the pinned base, excluding commits already on main; landed prerequisites are not the test writer's edits. Reverted edits and invented merge resolutions still count. Its `cointos finish --complete` goes through `api.finishing`, which first runs `contracts.passing` outside the ledger lock: main merged with the packet commit must pass every registered command. If it does, the receipt (evidence `passing: true`) puts the task in review, and an integrator lands it through the ordinary gate. Otherwise the task settles done with acceptance via `tests`, and the record done at that commit, without an integrator or landing; its branch is archived (`refs/cointos/archive/`), keeping the commit reachable. An implementation or integration item's packet is the accepted test-contract items it depends on (`landing.tests_of`). Its `cointos finish --complete` goes through `api.finishing`: outside the ledger lock, with the task marked validating (exempt from silence checks; drains wait), `contracts.packet_check` checks out the committed code, merges the packet commits, and runs the commands they register beyond main's manifest plus any bundled in by a landing. A failure raises the API error back to the still-running implementer, showing each failing command's output and the test source around each location it names (`contracts.reveal`), and logs `packet tests failed`. Success records the receipt with `tests` (the packet commits) in its evidence; `lifecycle.evidence` refuses a checked receipt for any other commit. Projects without a test policy skip both checks.

**Landing gate (installed).** The integrator's `cointos review` fast-forwards to main, squash-merges and commits each packet commit as "Tests for ITEM", then stages the worker commit and shows the worker's receipt. The daemon's /api/land (`cointos/landing.py`) checks a clean exact candidate in a fresh detached worktree, within `timeouts.command_seconds` and outside the ledger lock. Landing requires the integration's current run, the exact submitted worker commit and a complete receipt, for every stage. Blocked receipts authorize assessment only. Test-contract candidates cannot change production. For implementation/integration, `contracts.packet_unchanged` uses the same `stage_history` attribution to forbid worker edits to protected paths and requires candidate tests to equal main merged with the packet. `contracts.suite` then runs every registered command on the candidate; each red one is rerun on main, and a command red on the candidate but green on main (or new) is caused by the item. Caused failures return the worker with those commands appended to its `bundled` tests and their output and revealed source as the review notes; a failure main already has is logged in the gate counts and does not block. Each command runs in a transient systemd unit capped at `memory.agent_limit_gb`, with no swap and whole-unit cleanup. Tracked changes made by tests are rejected. It checks run ownership and worker/candidate/main refs again before fast-forwarding main and settling the worker and its integration. A persisted `landing` record lets a retry settle a landing interrupted after its fast-forward; a commit that reached main without it is refused, and there is no separate accept path. The acceptance is the terminal lifecycle authority: it writes the record's `done`, and the runtime queue leaves republish when their text changes. Concurrent-main conflicts leave main and task acceptance unchanged. An integrator resolves/stages the conflicting files preserving both sides and repeats `cointos land` with the same summary; the command commits the resolution and runs the same exact-candidate gate. Duplicate validation is rejected, draining waits for active landings, and an agent waiting on its bounded daemon validation is exempt from event-silence recovery.

Implementer edit-tool permissions deny configured protected paths. Shell access and Git remain same-user capabilities, so hiding a packet is a CointOS policy, not an OS sandbox: an implementer could find archived refs with raw Git. Stage correctness remains a review responsibility. A packet test that contradicts the contract is reported blocked and reaches a manager; integrators cannot repair tests inside an implementation landing. Skeletons retain their reviewed acceptance and the full-suite check. The explicit incorporate API can settle implementation already on main only with pinned main/worker commits (the worker commit must be its receipt's, which must be complete), every production file the worker changed identical on main (`contracts.incorporated`), and its packet's tests already on main (`contracts.tests_landed`); a rewritten file needs an integrator's landing instead. supersede repairs failed prerequisite edges without pretending that the failed task was accepted.

Evidence: `cointos/contracts.py`, `landing.py`, `lifecycle.py`, `api.py`, `queues.py`, `spawner.py`, `recovery.py`, the CLI and role prompts. On real Git repositories, tests/test_landing.py exercises hidden and passing packets, revealed failures, refused receipts, blocked work refused at the gate, the full-suite gate, bundled-back tests, incorporation and retry; tests/test_contracts.py covers production paths, protected-path immutability and how a command runs; tests/test_queues.py covers the `Relies on:` requirement and dispatch refusal; tests/test_recovery.py covers budgets, exhaustion continuation and the one-time warning.

**Concern pipelines.** Break work by interface and responsibility, not a few large features. A parser may separate lexical recognition, value construction and serialization; the precise stages depend on its contract. Each item gives one outcome, exclusions, inputs/outputs, error and ownership rules, affected area, dependencies and an executable check. It contains one hard algorithm or edge-case family. Each manager run advances one abstraction boundary and elaborates only the next one to three concerns, retaining an unexpanded frontier in the project plan. Queue records remember which task proposed them (`proposed_by`). Queued children continue without a dependency-bound continuation manager. Scope-completion evidence still requires model/reviewer judgment; the daemon does not infer product completeness from plan prose. Workers independently reject oversized or contradictory assignments as blocked with concrete evidence. An integrator verifies a blocked report and finishes blocked when the assignment needs managerial correction instead of returning the same impossible brief. The daemon automatically routes failed worker items, including briefs refused by the dispatch check, through one bounded manager pass with assignment and receipt evidence, independent of report phrases. The manager may revise a false brief (or revise it to name finished branch work, so its worker submits that) or replace the item with smaller children. A completed revision does not accept failed work; a blocked or exhausted manager blocks the record without another automatic pass and alerts the user.

**Reverse review and recomposition.** Workers report the boundary they expose and assume, checks and unresolved mismatches; the owning interface leaf states the current contract. The integrator checks one item's boundary against the actual change and neighbors. A manager command asking for a survey or coherence review compares a small set of neighboring contracts at one common abstraction level and records that layer's contract or queues one bounded coherence check. Further recomposition occurs through later bounded commands. In addition, the global retrospective test auditor samples recent accepted product work, compares its tests with the owning specification, runs bounded relevant suites, and queues at most one manager command for a concrete semantic enforcement gap.

**Small gardeners.** Every enabled project's knowledge tree and each explicitly configured CointOS-owned tree participates automatically. The spawner (`spawner.tree_work`) chooses up to `garden.leaves_per_pass` leaves: random for routine passes, brown then yellow for health repairs. A gardener verifies only that batch plus necessary neighboring evidence, lands corrections and submits its receipt, whose validator requires a landed branch and a clean worktree. Selected leaves still non-green on main are recorded in the receipt and reported through an alert; the bounded pass ends instead of retrying until the whole tree is green. An unchanged health set is retried only at the routine interval. Separate tree-audit tasks examine one structural concern across representative owners (duplicates, log-shaped answers, stale routes or contradictory abstraction levels). Both kinds share per-tree exclusion.

Role prompts, queue validation, the packet check, the landing gate and runtime budgets implement these bounds. Mechanism coverage is green; live task-quality and sustained-flow acceptance remain in `what/is/the/plan.md`.
