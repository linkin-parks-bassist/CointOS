Requirements for the CointOS MVP. The vision is `what/is/cointos.md`, the design is `what/is/the/architecture/of/cointos.md`, and the working rules are `how/to/keep/cointos/simple.md`.

## Requirements

1. **Coin always answers.** A Telegram message gets a visible reply within 15 s whenever the machine is up. Coin can report status, list agents, queue work, submit general commands, manage registered projects, request the canonical scout, launch an explicitly scoped ad-hoc operator, and stop, halt and restart the system.
2. **The workstation stays usable.** The desktop stays responsive while agents run. The user's own local agent sessions outrank background agents.
3. **The GPU stays busy.** With work available, both work-model lanes are in use most of the time, shared among more live agents than lanes.
4. **Work moves without the user.** Agents pick up urgent and queued items, carry out general commands, survey configured projects for loose ends. Runtime queues show scheduling status, projects are enrolled and prioritized through a durable registry, and results land as commits in the project repositories.
5. **Agent work continues.** A task (a queue item or a request from the user) persists until it is done or blocked. If the agent working on it stops for any reason, a new run resumes the task, continuing the same OpenCode session where it exists for ordinary death, pressure or daemon replacement. A configured generation-time/token budget bounds each run; exhaustion permits a finite number of fresh-session retries preserving branch/files and canonical task evidence, then fails the run assignment. Failed worker items receive one bounded manager pass; an unresolved or exhausted manager escalates to the user. Lane waits, prefill and tools do not spend that budget. Fresh recovery carries a bounded packet of outward statements, tool evidence and Git state, excluding hidden reasoning. Worker items that consume substantial generation without leaving a durable branch artifact recover before the larger total run ceiling. Tasks carry validated daemon-managed budget metadata; effective limits are pinned at creation and stated as an FYI at the end of every new/resumed run's launch prompt, together with the exact uninterrupted-thought cap and an instruction to decide succinctly before acting. Managers may configure child budgets through the daemon. Active runs keep their limits.
6. **The system notices problems.** A stopped or stuck agent, an idle lane with work waiting, or a looping agent is detected and handled within a minute, and shown to the user.
7. **The scheduler is pre-emptive.** The user has intended this since inception. A lane can be taken from the agent using it at any moment, mid-generation, and given to another; the interrupted agent resumes later where it stopped, losing no work. Nothing an agent does holds a lane beyond the scheduler's decision. (the user, 2026-09-26: "it has been the intention since inception that the cointos scheduler would be pre-emptive.")
8. **One control surface.** `cointos status|agents|jobs|check|stop|go|restart|halt|up`, `cointos project ...`, `cointos agent run ...`, Coin and the dashboard at `http://127.0.0.1:4200` expose the ledger and supported controls. Active and queued work stays visible; terminal task and queue history is folded and can be cleared through the daemon without removing active/queued work or terminal prerequisites still needed by that frontier.
9. **Pipelined work at every level.** Every assignment is one bounded stage. It consumes a bounded input and leaves a checkable artifact, an explicit boundary and the next handoff. The rule covers decomposition, implementation, verification, integration, discovery and recomposition. New software is built from small skeletons, then a focused test contract before each function, then bounded integration layers. Agents calculate with code and tools. Failed worker items, including integrator-confirmed blockers and exhausted retries, automatically receive one bounded manager pass with the original assignment and receipt evidence. Routing uses lifecycle state, not report wording. The manager may revise the false brief or replace the work; unresolved manager blockers and exhausted manager retries require the user. Managers record the remaining frontier in the project plan and finish their bounded stage with completion evidence or a blocker. Queued children continue independently. Periodic system-wide scouts may rediscover a concrete loose end and enqueue one manager command; when they require the user, they alert them through Coin. All roles terminate through one daemon-owned, idempotent completion receipt and lifecycle reducer; transport finish markers, arbitrary text, prompt instructions and retry count are not semantic completion authorities. Integrators may enqueue one same-project follow-up exposed by acceptance. `what/is/the/shape/of/cointos/work.md` owns the details and the current sizing calibration.

10. **Implementation test integrity.** Tests are adversarial contracts written before implementation. Implementation commits cannot change protected tests or harnesses; all accepted tests covering code added or changed must pass on the exact candidate before merge. Unrelated red tests are allowed. Scheduled tasks carry stage and reasoning-effort metadata: the global default is low, and test-contract workers and managers default medium; explicit task overrides still win. Front-load effort into the test contracts; failed implementation gates return the task to its implementer with actionable failure details. Coverage declarations are reviewed, not inferred as complete from a green gate. After recent accepted product work, a periodic roaming test auditor samples one landing against its specification and tests, runs bounded suites, and queues at most one manager command for a concrete semantic coverage gap. This post-work loop targets eventual correction rather than requiring every landing to be perfect. Integration cannot weaken accepted tests/contracts and must validate carried production changes against prior accepted contracts. Already-incorporated implementation requires a daemon-verified receipt pinned to main and submitted worker commits before task settlement; ancestry or prose alone is insufficient. A verified acceptance receipt is the single terminal authority for task and queue lifecycle state: it marks the item done, removes obsolete blocker/decomposition state, is reconciled before dependency readiness, and triggers publication of the derived queue projection.

11. **Knowledge-tree maintenance.** Periodic gardeners perform bounded maintenance-only passes across the CointOS source tree and every registered project's knowledge tree. Structural tree auditing remains a separate slower pass.

12. **Least disruptive configuration and replacement.** Apply supported settings in real time; use a compatible live daemon restart for larger changes, preserving agents and models wherever possible; reserve full restart for incompatible changes. The live settings are scheduler.slice_seconds and scheduler.chunk_tokens, editable in seconds and tokens from the dashboard. This hierarchy is the user's direction of 27 September 2026, not a claim that all restart cases pass acceptance.

## Acceptance (seen live)

- **Soak:** 2 hours unattended with at least 4 live agents on the 2 work lanes. `cointos check` stays green throughout, and at least 3 queue items land with commits. Integrators explicitly signal the daemon after merging; it settles the records and their dependencies.
- **Coin under load:** 10 Telegram messages spread across the soak all get visible replies within 15 s.
- **Workstation:** The user uses the desktop normally during the soak without sluggishness. Their own local OpenCode session is served ahead of background agents.
- **Halt/up:** `cointos halt` mid-soak leaves no CointOS process running and no model loaded. After `cointos up`, the interrupted tasks resume.
- **Kill test:** killing an agent process mid-run is detected and its task resumed within 30 s, with `cointos check` green again afterwards.
- **Pipeline:** a request that enters through ordinary intake is decomposed, implemented, integrated and recomposed in bounded stages, with no manual decomposition, and the result meets its own acceptance.

`what/is/the/plan.md` lists the remaining acceptance work. Completed ledger tasks do not substitute for the scenarios.

## Recovery boundary

Automatic recovery is bounded and mechanical. It preserves tasks, stops distressed work, unloads and reloads models, and restarts services as configured. Catastrophic diagnosis and repair are for the user and a stronger remote agent. An autonomous Sole Survivor agent is off the current roadmap unless the user revisits the decision.
