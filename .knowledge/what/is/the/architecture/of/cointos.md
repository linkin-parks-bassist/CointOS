**CointOS is an operating system for agents.** The primitive is the agent. Model lanes are resources: a pre-emptive scheduler time-shares them among agents, the way an operating system time-shares CPUs among processes. Details not fixed here are for the builder to decide, within `how/to/keep/cointos/simple.md`.

## Concepts

- **Agent:** a worker with a task, a role and a conversation (an OpenCode session), living until its run ends. Agents are what CointOS is about; everything else serves them.
- **The four Rs:** an agent is always *Reading* (the model is reading its context into a lane), *Reasoning* (the model is thinking), *Writing* (the model is writing its message or tool calls), or *Running* (its tools run: commands, file edits, knowledge-tree lookups); or else *waiting* for a lane. Reading, reasoning and writing make up a thought, which needs a lane; a running agent needs none.
- **Thought:** one span of thinking, from the agent's conversation to the point where the model hands back control with a message or tool calls. A thought can be interrupted and resumed any number of times.
- **Context:** the agent's conversation as the model holds it: a token sequence and the lane state computed from it. A context is *resident* on a lane, *saved* as a snapshot, or *cold* (only its tokens are known, and the model must read them again). **A context is identified by its tokens**, not by who owns it: a lane is *warm* for a thought when the tokens its state holds begin the thought's tokens, and a snapshot is found by a digest of the tokens it holds. So concurrent conversations of one owner never collide, and an agent resuming a task's session (even after a daemon restart) finds that task's context. Owners (a task, Coin, David) govern snapshot lifetime, divergence cleanup and shared-start eligibility, but do not replace token identity.
- **Lane:** one execution slot of a loaded model, holding at most one resident context. A model has a fixed number of lanes, set when it is launched.
- **Class:** an agent's priority, highest first: Coin, David's own sessions, background work.

## The scheduler is pre-emptive

- **Any lane can be taken back at any moment.** The scheduler decides which thinking agents hold lanes. It never waits for an agent to finish a thought.
- **A switch** takes a lane from one agent and gives it to another: the outgoing context is saved if still useful and memory permits, and the incoming one is restored if a usable snapshot exists, otherwise read from its tokens. The outgoing agent's thought is suspended exactly where it stopped and loses nothing.
- **Granularity:** a thought advances in steps, each running to its own end: a step reads up to `read_chunk_tokens` of a context the lane does not hold yet, or, once it is read, generates up to `chunk_tokens`. A switch happens between steps. So a lane always holds exactly known tokens, and an agent waits at most one step plus one switch for a lane it is owed. (A step is not cut part way: llama-server notices a dropped request only when it next writes. The one exception is below.)
- **A lane whose state the server dropped.** The model server can discard a lane's state between requests without warning (seen twice after a restore; the next 96-token step then re-read a 25k context for 150 s). Every step streams the server's prompt progress, whose first report says how much of the context it kept before it reads anything. If it kept less than the lane was known to hold, less one `read_chunk_tokens`, the step is abandoned at once (the server stops within a batch) and the lane holds nothing known; a snapshot restored into it that did not survive is forgotten. The thought goes on through the ordinary switch and bounded reads.
- **Reading and generating.** A thought is *reading* while no lane holds its context yet (a truly cold first turn, or a context whose snapshot was lost), and *generating* once the model is writing. The agent's state shows which.
- **Turns.** An agent's turn on a lane runs from when it gets the lane until it gives it up, across consecutive thoughts.
- **Policy**, applied at every step boundary, whenever an agent starts thinking, and every tick (a slice runs out between events):
  1. A thinking agent of a higher class takes a lane from a lower class at once. It takes a lane whose holder is generating before one whose holder is reading, so a cold read is displaced only when there is no other lane.
  2. Among equals, a reading holder keeps its lane until its context is read. A generating holder whose turn clock has reached `slice_seconds` gives the lane to the equal that has waited longest. The slice clock starts when the turn's opening read is done and continues through quick tool-call grace (a thought continuing the turn reads only its tool's result, which does not restart the clock), so a cold agent is never pre-empted the moment it finishes reading, and a burst of tool calls cannot hold a lane past its slice.
  3. A tool call yields the lane, like a system call, with a finite cooldown: while the turn is inside its slice, the lane stays held for its agent for `yield_grace_seconds` (never past the slice's end), and a next thought arriving within that grace continues the same turn, so a burst of quick tool calls is not switched out. Once the slice is over, a tool call is a plain yield to whoever waits. Only a higher class may take a held lane.
  4. A thought is placed on the cheapest lane open to it: the one it holds or that is held for it, then a warm one, then a free one, then an unreserved one.
- **Contexts stay resident when nothing needs the lane.** When a thought ends, the agent's context stays on its lane. A switch need not save/restore it while it stays resident. Checkpoint saves at the end of a cold read, shared-start saves and graceful-stop saves are separate from switching.
- **Shared starts.** Agents of one role share a long common start (tools, system prompt, role). When a context being read shares at least `shared_prefix_tokens` with a live or resident context of a different owner on the same model, the read stops exactly there once and saves that start as a shared snapshot. Later contexts can restore it through the ordinary longest-snapshot match while it remains available and restoration fits in headroom.
- **Checkpoints and suspended states.** When a thought's context has been read, before it generates, the lane holds the committed prompt except its final token (the hybrid model needs that token to extend the state); a *checkpoint* save is attempted if memory permits. A thought stopped part way (switched out, or on a graceful stop) is saved as a *suspended* state. A run that dies or is stopped mid-thought abandons that thought; its conversation goes on from the checkpoint, with any usable checkpoint avoiding a full reread. If the checkpoint could not be saved or was evicted, the committed conversation must be read again.
- **One line of snapshots per conversation.** A checkpoint supersedes its conversation's older snapshots; a suspended state supersedes only older suspended ones, so the checkpoint outlives an abandoned thought. A task's conversation is one line of history, so when its next thought starts, the task's snapshots that do not begin the new context are forgotten. Coin's and David's snapshots, which may belong to several conversations at once, leave by least recent use.
- **Reservation:** one lane of the front-desk model serves only Coin, so background work cannot occupy that lane. Model availability, Coin request contention and Telegram latency still bound visible response time.
- **Bound:** a thought generates at most `max_thought_tokens`.

## Backend layer

The core speaks only the concepts above. One backend module translates them for a particular model server, so no llama-server or Lemonade detail appears outside it. The interface:

- **launch(model, shape)** and **kill(model)**; **models()** reports what is loaded, in which shape, with how many lanes.
- **render(model, conversation)** turns a conversation (messages and tools) into context tokens.
- **prefill(lane, tokens, held)** makes the lane, known to hold `tokens[:held]`, hold exactly `tokens`, reading only what it does not hold yet.
- **think(lane, tokens, held, max_new)** extends a context on a lane, streaming the new tokens, and stops at the end of the thought or after `max_new`; the lane then holds every token but the last one received.
- Both raise **Lost** before reading if the server no longer holds what the lane was known to hold.
- **save(lane, name)**, **restore(lane, name)** and **forget(name)** move contexts between lanes and snapshots.
- **read(model, reader, tokens, final)** turns a thought's tokens into what the agent sees: reasoning, message text and tool calls.

The first backend, for Lemonade-managed llama-server (`how/does/lemonade/serve/models.md`), uses raw token completions with `id_slot`, slot save and restore to a snapshot directory in `/dev/shm`, and the model's own chat template and tool-call format.

## Processes

- **`cointosd`**: one long-running daemon (Python standard library, one systemd user unit), the only writer of the ledger. It contains:
  - **Gateway:** the OpenAI-compatible endpoint on loopback through which every agent thinks (OpenCode agents, Coin, David's own sessions). A chat request starts a thought for its agent; the reply streams back as the thought advances, however often it is suspended.
  - **Scheduler** (above), **spawner**, **guard**, **self-check**, and a small loopback **API and dashboard**.
- **Agents:** OpenCode processes the daemon starts, each in its own git worktree with its own gateway key.
- **Coin:** a separate small service (Telegram in, replies out), so it can report on and restart the daemon. It thinks through the gateway and uses the daemon's API and the kt MCP server.

## Installation and projects

The source repository is separate from the installed runtime. `scripts/install` copies runtime code, roles, configuration and service assets into `~/.CointOS/`; services run there. It is a standalone script, not a CLI subcommand. Its runtime `.knowledge` tree is globally readable and explains CointOS and the current queues. The daemon owns scheduler records. Each managed project is an ordinary repository under `~/Projects/` with its own kt-initialized orientation, spec, plan and broken leaves. Worktrees are siblings under `~/Projects/.worktrees/<project>/<task>` on `work/<task>` branches. Todo is configured at `~/Projects/todo-cli`; the sandbox retains its unrelated utilities. Installation requires no running agents and preserves pause.

## Config and ledger

- `config/cointos.json` owns every operational number: models and their shapes, reservations, classes, `chunk_tokens`, `slice_seconds`, bounds, memory limits and the ladder's timings, spawner limits, intervals, ports, `timeouts` (backend requests, agent start and stop, API, commands, stop-time save), Coin's Telegram timings, viewer timings, the dashboard's live rate and retention counts. Only sub-second spin-wait granularities inside waiting loops remain in code, as implementation detail.
- `state/cointos.json` is the ledger, written atomically by the daemon only, holding the ledger lock through serialization and replacement so API and tick saves cannot overtake each other: agents (role, task, state: starting, reading, thinking, waiting or running; reasoning versus writing is in its live phase; lane; what it is doing), lanes (model, resident agent), saved contexts, recent history and self-check results. The CLI, the dashboard and Coin read it.

## Models

The backend's `models()` is the source of truth for what is loaded, because the model server is shared. Every `model_check_seconds` the daemon compares it with the config and launches any wanted model that is missing or in the wrong shape, one at a time. When a model goes away, its resident contexts are lost; their agents restore a matching snapshot if usable, otherwise read their contexts again when they next run.

## Agents

- **One owner per agent.** Each run is an independent transient `cointos-agent-<id>` systemd user unit running the OpenCode server and client. The unit's memory is capped at `agent_limit_gb` with no swap, so a runaway tool is killed inside its agent; without the cap, an agent's test once drove memory and swap until systemd-oomd killed Lemonade, taking both models down. A daemon thread follows its event and exit files and settles the task. The run outlives a daemon restart.
- **One way to end.** For daemon-directed stops, the agent first leaves the ledger with its task settled; then its systemd unit is stopped. Runs that end externally are settled when observed. Until `exit_grace_seconds` pass, it is listed as exiting. A task's snapshots are forgotten when the task is done or failed, since only then is its conversation over; a requeued task, or one awaiting review, keeps them for its next run. Only Coin (`coin`), David (`user`), shared starts (`shared`) and running or waiting ledger tasks are live owners (`lanes.live`), so a save finishing after its task ended or was forgotten is discarded. At daemon start, `lanes.forget_orphans` forgets snapshots whose owner is neither one of those three nor a ledger task.
- **Settling:** workers finish their stage by committing code and `.work-report.md` (`Status: done` or `blocked`) on their branch, then await review. Integrators finish after an explicit accept or return API action. A command or decomposition manager commits and merges its planning changes, then signals `finish`. A gardener or auditor must stop normally with its branch merged and worktree clean; selected leaves still non-green are reported, not retried endlessly. Other normal completed runs settle normally. Unfinished runs requeue up to `max_runs_per_task`; operator and guard stops refund the attempt. Halt settles and persists before acknowledging, preserving pause.
- **Silence:** `checks.silent_agents` is the shared predicate for recovery and self-check: no outstanding thought and no OpenCode event or thought end for `agent_silent_seconds` (currently 30). A thought's end, however it ends, counts as activity, so an agent whose long thought fails is not ended as silent at once. It covers startup, tools and between-request stalls. Reading, generating and lane waits are exempt because they have a thought. The tick stops silent runs and requeues their task, charging an unfinished attempt. This is an event-silence bound, so a long tool that emits no OpenCode event can also reach it.
- **Looping:** an agent whose thoughts produce the same output more than `max_identical_thoughts` times in a row is stopped and its task requeued.
- **David's own sessions** think through the gateway with a user key, in the user class. A user thought updates `user_last_thought`; the spawner starts no new background agents for `user_quiet_seconds` after that request began. This is a timed admission rule, not continuous hosted-session detection.

## Autonomy

- The spawner fills available capacity up to `spawner.max_agents` whenever admission allows it; agent count is independent of lane count because tools use no lane. Current focused-test settings cap agents at two with one work-model lane. `trees: []` temporarily disables gardener/auditor admission; the cancelled periodic survey's cadence remains recorded, so it is not immediately recreated. Existing queued/command work and integration still use ordinary admission. Task ranks affect what starts, not GPU weighting: all autonomous roles currently use the background class. Ambient/focused modes, mutable project/kind priorities and weighted/count-based lane shares are deferred design requests, not implemented.
- Every task has a *place*, the project or tree it works in, and a *rank*. Existing waiting tasks are resumed first, in rank order; then new work is created, also in rank order: a tree with brown leaves (gardener), integrating a finished item (integrator: finished work lands before new work starts, so branches stay close to main), decomposing an item a worker returned as too big (manager), a tree with yellow leaves (gardener), queued items (worker), general commands (manager), a periodic survey (manager) or routine gardening pass, maintenance (steward). Queued items and general commands rank by their daemon-owned priority, so urgent work is simply listed first; a waiting item task takes its current position each pass, so a manager's reordering applies. Among gardening tasks, the worse tree (more brown, then more yellow) comes first.
- **Gardening is per tree, not per project.** Configured trees name a repository, root and landing branch. Every garden.check_seconds the daemon reads health with kt status (no proofs). A changed non-green set starts a repair batch with brown first; otherwise garden.every_seconds selects up to garden.leaves_per_pass random leaves (currently 3). Task brief stores selected root-relative paths. A gardener verifies those leaves and necessary neighboring evidence, lands corrections with cointos merge and ends. Settlement checks normal stop, clean worktree and branch ancestry on main. Selected paths still non-green on main trigger an alert and remain unresolved; neither they nor unrelated unhealthy leaves force a finished batch to repeat. A changed remaining set can schedule the next batch; an unchanged set waits until the routine interval. A separate tree-auditor role runs at garden.audit_every_seconds (currently weekly), examines one structural poisoning concern across representative owners and has the same landing requirements without a selected repair batch. At most one garden-kind task runs or waits for a tree, shared by gardeners and auditors; both count in max_agents. The global non-git root is not tended.
- **Pipelined work at every level.** Every agent run is one bounded stage that consumes a bounded input and leaves a checkable artifact, an explicit boundary and the next handoff. Managers advance one decomposition layer and elaborate the next one to three concerns, keeping the remaining frontier in the parent idea; their output may itself need another decomposition stage. For new software, the planned dependency graph runs from small type/signature/stub skeletons through a focused test contract before each matching function implementation, then through bounded integration layers over already-tested parts. Each worker item specifies one construction stage, interface, assumptions, error/ownership rules, exclusions, dependencies and executable acceptance. Workers refuse oversized scope, compute with tools and record a branch-local boundary report. Integrators maintain the owning interface leaves. Integrators verify and land one item boundary. Manager surveys recompose one layer of neighboring contracts and leave further coherence work as bounded follow-ups. Maintenance, gardening and structural audit runs obey the same rule. These are prompt responsibilities, not a mechanically enforced semantic size metric. A separate reviewer scheduler is not implemented. what/is/the/shape/of/cointos/work.md owns the governing direction.
- **Runtime queues have one writer.** The daemon persists queue records in its ledger and publishes their current readable projection in runtime `what/is/queued.md` and `what/is/the/command/queue.md`. The tree contains Markdown answers, not JSON payloads. Project trees contain no scheduler leaves. Managers, CLI and Coin submit through POST /api/queue (`project`, `kind`, `name`, `brief`); kinds are queued, urgent and command. Urgent tasks go first. Stable numeric priority survives sorted JSON persistence; retrying the same proposal is idempotent. Commands describe general managerial actions, not only product ideas.
- **Dependencies.** A brief's `Depends on:` line names comma-separated task names. Only daemon-confirmed done records satisfy dependencies; Git trailers are not consulted. Unknown/blocked dependencies and cycles are reported. Decomposition blockers wait for a manager.
- **Decomposition.** An accepted blocked worker report containing `Needs decomposition:` schedules a manager. It proposes children through the API, then `cointos replace CHILD...` repoints dependents and retires the parent record. It commits and merges the remaining plan, then signals `cointos finish`.
- **Workers and integrators.** Workers commit code and `.work-report.md` on their branch and stop. One integrator per project reviews the oldest report. `cointos review` squashes the worker change and removes the branch-local report from the staged result. The integrator checks code and evidence and maintains the project's tree, plan and broken leaves. `cointos land "summary"` commits with the worker's account, merges, then calls /api/accept with its commit. The daemon checks the commit is the integrator's HEAD and is on main before settling the worker and dependencies. A lost response can be retried with the same command and summary. `cointos return "notes"` requeues the worker with notes; its branch/session survive. No landing trailer or project queue deletion is required. Branches are removed after integration finishes.
- **Landing.** `cointos merge` finds a task by its worktree, merges main into the branch and fast-forwards main. Conflicts remain in the worktree for the owner to resolve; dirty or conflicting work does not land. Workers cannot land their own branch. Managers, gardeners and auditors use this for their bounded changes.
- **Knowledge ownership.** Integrators maintain project knowledge and remove completed plan steps as part of acceptance. Managers maintain the remaining planning frontier in their planning stages. Workers report evidence and proposed knowledge corrections on their branch. The daemon exclusively owns scheduler bookkeeping; runtime queue leaves must not be edited by agents.
- Routine maintenance runs only if `maintenance_project` is also configured in `projects`; without CointOS in projects no CointOS steward is spawned. Sole Survivor is off the current roadmap. The guard handles known recovery mechanically; David brings in a stronger remote agent for catastrophic diagnosis and repair.

## Memory

The machine is David's workstation first. Memory is one pool (unified GPU memory), managed by one rule.

- **Headroom** is available memory (`MemAvailable`) minus `reserve_gb`, the memory always left for David's normal use. Everything CointOS allocates (models, snapshots in `/dev/shm`, agent processes and what their tools run) shows up in this one measurement.
- **Admission uses estimated headroom.** Launching a model needs its `memory_gb`, starting an agent needs `agent_memory_gb`, and saving a context uses size estimated from existing snapshots of that model. With no prior snapshot the estimate is zero and the first save is measured afterwards. This is admission accounting; the hard bound on an agent's later allocations is its unit's `agent_limit_gb` cap.
- **The model server's allowance counts too.** Lemonade runs in `inference.slice` with its own memory budget (`memory.high`), and snapshot files in `/dev/shm` are charged to it. Budget pressure previously caused systemd-oomd to kill Lemonade; crossing this budget is not itself a synchronous kill instruction. So headroom is the tighter of the machine's (available memory minus `reserve_gb`) and the server's (its budget minus its anonymous and shared memory; page cache it drops cheaply). The backend reports the server's.
- **Snapshots give way first, a tier at a time.** They are the only elastic memory. Whenever headroom is negative, or an allocation needs room, the least recently run snapshots in memory move to disk (`disk_snapshots`, at most `disk_snapshots_gb`, whose own least recently run snapshots are forgotten to make room), or are forgotten when the disk tier is full. A snapshot on disk comes back to memory for a restore if it fits; otherwise its context is read again. Moves run outside the daemon's lock.
- **Snapshots outlast everything but a reboot.** Snapshots in `/dev/shm` survive a daemon restart, a killed model and a killed Lemonade; only a reboot or power loss wipes them. When the machine shuts down (systemd reports `stopping`), the daemon attempts to move eligible memory snapshots into the bounded disk tier. Warm recovery requires a completed move, persisted metadata and a matching conversation; power loss can prevent it. Reboot recovery still needs a live demonstration. No snapshot is ever copied periodically: a snapshot is a whole state (about 3 GB for a 35k-token context), so periodic copies would cost terabytes of writes a day.
- **A snapshot is a cache, never a record.** OpenCode's session is the record of a conversation, tool calls and results included. A snapshot is used only when its tokens begin the conversation as it now is, so an old snapshot is never wrong, only shorter: the model reads, and does not repeat, whatever happened since.
- **Giving memory back: the ladder.** Headroom is the leading signal (it falls before anything stalls). While it stays negative after saved contexts have left memory (rung 1, which happens whenever needed), the guard climbs one rung, then waits `shed_step_seconds` for the effect to show before the next: rung 2 stops background agents (uncharged, requeued; checkpoints keep their contexts) and admits no new ones; rung 3 unloads the work model (about 39 GB). The core stays: daemon, front-desk model and Coin. **Distress**, memory pressure (PSI `full avg10`, the share of time all tasks were stalled on memory, above `max_psi`) sustained for `distress_seconds`, is a lagging signal and a shortcut to the top rung. Swap in use is not a sign of distress, since it lingers after pressure is gone. Coming back: after `calm_seconds` without shortage or pressure the guard steps down a rung (from rung 2 straight to normal), and leaves rung 3 only once the work model's `memory_gb` fits. Each rung change alerts Coin. A process that allocates faster than a one-second tick (for example a tight malloc loop) is the kernel's or systemd-oomd's to stop; the ladder ensures CointOS stays out of the way and recovers cleanly afterwards.
- **Lanes and memory.** A model's KV-cache is allocated at launch for its whole context (`ctx_size`), split among its lanes; fewer lanes of the same total context free nothing. Changing the shape (lanes or context) needs a relaunch: llama.cpp does not resize a KV buffer in place. With the weights in the page cache a relaunch of the work model takes about 10 s; a reshape rung (relaunch with less context, restoring contexts from snapshots) is a candidate under discussion with David, not built.

## Halt

- `cointos halt` requests durable uncharged settlement from the daemon, then stops its services and remaining agent units and kills the models. If the daemon is unreachable, the CLI reports that and performs process/model cleanup; it cannot retroactively settle work through a dead ledger owner. An API error other than unreachability aborts the CLI before unit teardown. `--keep-coin`, used by Coin's own halt tool, retains Coin. `cointos up` starts everything from the config.
- **On daemon restart**, agent units remain alive. The new daemon adopts prior agents with persisted gateway keys and tasks, follows their event files, and settles runs that ended meanwhile. Unknown agent processes are stopped; running tasks whose agent is absent return to waiting. A retried thought can use a matching checkpoint. This is distinct from `cointos halt`, which explicitly stops agent units too.

**Discarding invalidated work.** Pause first with cointos stop and verify the agent units have exited. Queue records are daemon-owned; never delete project leaves to influence scheduling. Delete only the selected task's OpenCode session, run directories, worktree and work/ branch. The loopback POST /api/forget-task with {"task": TASK_ID} removes that task's snapshots and ledger record, clears its resident-lane owner so a later stop cannot save it again, saves before acknowledging, and is idempotent; it rejects requests unless paused with no ledger agents. It does not remove queue leaves or Git/OpenCode artifacts itself. This keeps the daemon the only ledger writer. Preserve already-landed work and unrelated sessions. Remain paused until work should resume.

## Self-check

Every tick the daemon checks these invariants over the ledger; a violation shows on the dashboard, in `cointos check`, and is sent to Coin:

1. No lane is free (and not held for an agent's grace) for more than `idle_lane_seconds` while an agent is waiting to think on that model.
2. A waiting agent that outranks a lane holder gets a lane within `preempt_seconds`.
3. No waiting agent is passed over for more than `starve_seconds` by an equal that holds a lane past its slice (and is not reading), counted from when that slice ran out.
4. No agent is silent for longer than `agent_silent_seconds`.
5. No agent repeats the same thought more than `max_identical_thoughts` times.
6. Every agent process belongs to a ledger agent or an exiting one (`no stray agent processes`). The run supervisor owns unit exit detection, event draining and task settlement: process absence before settlement is expected, including successful completion. Unfinished runs still requeue or alert on exhausted attempts; silence recovery remains separate.
7. Headroom is not negative and there is no distress.
8. No queue item waits on a dependency that can never be done (`no item waits on a dead dependency`).

## Watching

The dashboard shows agents first in full-width balanced rows, with at most three cards per row and nondecreasing density downwards: one card fills the width, 3 → [3], 4 → [2,2], 5 → [2,3], 6 → [3,3], 7 → [2,2,3]. Narrow viewports reduce capacity to two or one. agentRowSizes divides the count across the minimum number of rows, placing smaller rows first; six CSS grid tracks let each row fill the width while preserving card DOM nodes. Cards show what each is working on, its state as one word with its details (Reading, Reasoning, Writing, Waiting, Running, Starting), its words as they stream, and in its corner its uptime, the tokens it has written and its speed while writing (otherwise `idle`). Then the machine (lanes, memory, self-checks), then the work, with finished work folded away. `/api/live` streams agent cards and memory at 10 Hz; the full ledger is polled once a second. Card elements update in place. The memory donut retains its original five-part display: Operating System, Model weights, KV-cache, Saved contexts and Free. Configured loaded-model weights and KV capacity remain unscaled, and saved contexts use their measured file bytes. Because MemAvailable includes reclaimable model-weight pages, the renderer uses it only to find non-reclaimable use; it subtracts KV and saved contexts to estimate Operating System, then assigns the physical remainder to Free. Small CointOS process overhead remains inside Operating System, an accepted close-enough error. The guard is unchanged and continues to use MemAvailable plus the server budget. The dashboard uses the ordinary RAM convention: configured model values are already GB, while byte counters are divided by 2³⁰; every displayed value is labelled GB. Operational CLI and ledger arithmetic retains its existing units.

**Viewers** are pop-up terminal windows on David's desktop, each showing one live agent (`cointos view N` attaches OpenCode's live view to whichever agent holds slot N). The daemon gives each started agent a viewer: an idle open window first, so idle monitors are captured by new agents, else, while David has asked for them with `cointos view --all` (until `--off`), a new window, up to `max_viewers`. A window David closes frees its slot.
