**Construction pipeline.** Plan new software as an assembly graph, then advance only its next small frontier. Begin with small skeleton tasks that establish a few related data structures, signatures, ownership/error contracts, stubs and build seams without implementing the algorithms; they fix the names both the test writer and implementer rely on. Then, for each function or similarly small behavior, the user's packet rule (2026-10-06): code travels with its tests. The manager queues a test-contract item whose brief is the behavior's contract, and an implementation item with the same contract that depends on it. Separate workers write the tests and the code from that contract without seeing each other's work: the test writer encodes intent without implementation bias, and the implementer cannot code to the tests. Every completed test packet first receives independent integrator review of its contract and witness representability. Reviewed tests that fail on main are accepted without landing and stay hidden; when the implementer finishes, its packet runs and failures go straight back with only those tests revealed. The integrator lands code and tests together after the suite verifies the candidate introduces no new failures. Existing-main failures are measured and reported separately; acceptance is not a claim that every main test is green. Tests already passing on main have nothing to wait for: they are reviewed and land at once. Bounded integration tasks then join a few already-tested pieces and test their shared boundary, building upward through pre-planned layers until the full system is assembled. Independent chains may run in parallel after their shared skeleton lands.

**Enforced construction stages.** Worker tasks/records pin skeleton, test-contract, implementation or integration (implementation by default), plus optional reasoning_effort. Manager commands have no stage. Brief-only revision retains the existing stage, effort and budget limits; explicit budget fields merge with existing limits. `how/to/revise/queued/cointos/work.md` owns the revision procedure. Reasoning defaults come from `reasoning` in the configuration (test-contract workers and managers have their own entries); integrations use their role default without inheriting the worker's explicit effort/budget overrides. Existing tasks retain their pinned settings, and explicit daemon-owned task overrides still win. Front-load effort into adversarial tests; implementation/review remains bounded. cointos reasoning PROJECT:TASK LEVEL changes future replies without altering a thought already in flight; a changed template prefix may require rereading context. CointOS mechanically closes each uninterrupted reasoning block at its effort's `reasoning.budgets` entry, then lets the same reply answer or call a tool. There is no lifetime reasoning penalty: tool calls are treated as forward motion.
