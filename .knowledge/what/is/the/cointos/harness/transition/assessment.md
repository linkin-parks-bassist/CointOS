CointOS is assessing OpenCode 2, alternative harnesses and a bespoke runner with usable phone control. Assessment is authorised; no replacement or adoption has been selected. Preserve the installed OpenCode 1.18.35 integration and live sessions during evaluation.

Separate the coding harness from its remote client. Initial shortlist:

- Paseo is the leading remote-client candidate on documented features: Android/iOS store apps, Linux/headless daemon, OpenCode and Pi native providers, direct Tailscale connectivity or optional encrypted relay. Its support does not establish attachment to CointOS-owned private servers or preservation of CointOS authority. Sources: https://paseo.sh/download, https://paseo.sh/docs, https://paseo.sh/docs/supported-providers.
- OpenCode 2 has a shared service/web interface with one-use pairing and optional encrypted remote tunnel. A third-party OpenCode Mobile client documents Android distribution and iOS TestFlight, v1/v2 connections and direct VPN paths. Sources: https://opencode.ai/v2/docs/cli/web, https://www.getopencode.app/docs/getting-started/.
- Pi is a harness alternative with custom OpenAI-compatible endpoints and a long-lived JSONL subprocess RPC interface. This is a plausible fit for the Python daemon, not proven compatibility. Sources: https://pi.dev/docs/latest/models, https://pi.dev/docs/latest/rpc.
- HAPI wraps OpenCode through ACP and Pi through RPC and offers web/PWA plus native clients. Its native installation guide currently describes source builds, so app distribution is less convenient than Paseo's documented store installs. Sources: https://hapi.run/docs/guide/agents, https://hapi.run/docs/guide/native-apps.

A bespoke runner prototype is authorised for isolated experiments, not production adoption. The architectural case is that CointOS already owns scheduling, budgets, worktrees, tool authority and checked completion; a native session loop could reduce translation between lifecycle models. That is a design hypothesis, not measured simplicity or reliability. Its difficult obligations include durable conversation/turn state, interruption, ambiguous tool effects and crash replay, context/compaction fidelity and inspectable transcripts. Acknowledgement ordering could become enforced control flow. experiments/native_runner now exercises the gateway, acknowledgement ordering, durable turns and restricted file tools. how/to/run/the/cointos/native/harness/experiment.md owns procedure, evidence and limits. Mobile access is a separate interface question; Paseo compatibility with a custom runner is unverified.

MCP/hook integration is feasible but not implemented in the prototype. cointos/mcp.py and the kt server already expose stdio MCP independently of OpenCode. cointos/kt_mcp.py demonstrates initialize, catalogue/schema conversion and calls, but is a deliberately narrow synchronous client: it discards unmatched/server-originated messages, lacks general timeout/cancellation handling, and flattens tool results to text. It is evidence of a route, not a general client to copy wholesale. Prefer a qualified MCP SDK for broader transports/capabilities. Keep server instructions, structured/image content, tool namespaces, role-bound identity and access/elicitation decisions explicit; do not enable every globally configured server for factory agents.

Hooks need contracts rather than imitation of an OpenCode plugin API. Startup guidance/proofs, before-tool policy, after-tool observation, pre-stop validation and compaction context have different failure/authority semantics. Existing resume and compaction plugins contain both OpenCode workarounds and required task/budget facts; discard the workarounds while preserving obligations. Restarted effectful MCP/hook calls share the prototype's ambiguous-outcome problem; timeouts/cancellation do not establish no effect. Kernel/tool confinement, long-running subprocess ownership and completion receipt checks remain necessary. MCP connectivity alone does not establish safe production integration.

Recommended assessment: compare OpenCode 2, Pi and a bespoke runner design against the same lifecycle requirements using disposable state and the CointOS gateway; evaluate Paseo separately as a phone client. Check streaming/tools and kt MCP, kernel confinement, permissions, exact session resumption, interruption and compaction recovery, event accounting and budget ownership. Determine how phone actions reach the same supervised session rather than creating competing owners. CointOS currently depends on private servers, native session metadata, a resume plugin and a version-specific attached-event patch; a binary upgrade is insufficient.

OpenCode 2 migration has concrete adapter work: its server/client contracts and plugin API intentionally break V1 compatibility. opencode.py currently parses serve startup text, builds run --attach, calls V1 message/summarize endpoints and parses sessionID/part/step_finish events. opencode_resume.mjs uses V1 chat.message and compaction hooks. Port these together and qualify exact unfinished-turn recovery without replaying completed tools. The V1 attached-event binary patch is version-specific and must not be applied to V2. CLI docs retain JSON run output, explicit sessions and standalone/private-server support, so isolation is plausible but untested. Permissions become ordered rules and outside-project access defaults to allowed; preserve kernel confinement and test actual denials. MCP catalog/execution timeouts separate. Installation normally replaces the same executable and config locations overlap: isolate executable/config/state during qualification. Sources: https://opencode.ai/v2/docs/migrate-v1/, https://opencode.ai/v2/docs/build/plugins/migrate-v1, https://opencode.ai/v2/docs/cli/commands.

Phone UX and provider documentation have been researched, not exercised. Production gateway scheduling, local-model reliability, session recovery and end-to-end mobile use remain unverified; focused prototype evidence does not establish adoption. Changing the harness alone does not establish acknowledgement compliance.
