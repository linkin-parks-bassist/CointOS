The requested standalone system owns agent daemons, durable jobs and their model execution, rather than only extracting a scheduling function. Clients can request a new job; the service knows the selected backend endpoint and model, maintains the backing agent runtime/session, and preserves enough file-backed state to recover existing jobs after service or agent-daemon restart. Its name, repository, concrete API and extraction sequence remain unsettled.

Backend configuration identifies where inference runs and the controls available. Local controlled backends should retain CointOS's preemptive scheduling and current KV-cache/resident-state, shared-prefix, snapshot/spill and restoration optimisations. Hosted OpenAI-compatible backends should receive ordinary requests and stream their results through the same durable job/session lifecycle. Agent-daemon location and inference location are separate: a local agent runtime may use a hosted model. Endpoint locality does not itself establish native execution capabilities; a plain chat-completions URL cannot promise step control or KV restoration.

Durable job, runtime-session and request identities must survive restart. Retain the authoritative agent transcript/native session store, tools and their outcomes, workspace, backend/model binding and explicit pause/cancel state. Runtime bookkeeping should reference the owning session store instead of maintaining a competing transcript. Reattach to a surviving daemon or restart its existing session where supported. Distinguish interruption, uncertain request/tool acceptance and verified completion; recovery must not silently duplicate effects or convert an explicit hold into resumed work. Backend cache files remain performance hints, not the source of job/conversation authority.

The current implementation provides evidence for the extraction boundary: scheduler.py is pure scheduling policy; lanes.py couples execution to daemon state, memory/capacity admission, snapshots and backend controls. opencode.py/opencode2.py, runs.py and sessions.py own agent-runtime launch, observation and retained-session mechanics. Extracting scheduler.py alone would omit required lifecycle and recovery behavior.

The design under discussion is a generic daemon-backed agent runtime with a shared durable job/session layer and backend-specific execution controls. CointOS would consume it while retaining its product/factory/role policies. Local native step preemption and hosted full-request execution must share lifecycle semantics without pretending their resumability guarantees are identical. Preserve live CointOS inhabitants during design and extraction; this direction does not authorize manual steering or changes to their assignments.
