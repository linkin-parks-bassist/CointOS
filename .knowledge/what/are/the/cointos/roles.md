CointOS combines `roles/_base.md`, one role file and one bounded assignment, followed by the run's daemon-owned budget notice. Everything before the assignment is identical for every run of a role so the backend's shared-prefix cache holds; task-specific text starts only inside the assignment, after its project/location line. That second line is an identity line built from the task record (`Task: <id>, a <kind> task. Your role: <role>.`), so an agent never infers its role; its `cointos` commands act as that task with that role's permissions. Every role follows the bounded-stage rules in `what/is/the/shape/of/cointos/work.md`. Every agent role ends its run with exactly one completion receipt, which the daemon validates against the role's artifacts (`what/is/the/agent/completion/model.md`); final text, finish markers and process exit never complete a task. A role is fixed by its task kind (`cointos/schema.py`); a `command` queue item runs as a `breakdown` task with the manager role. Every role learns CointOS's commands from the runtime tree's `what/is/cointos.md`; a missing operation is reported (`--blocked` or `cointos attention`), never found by reading or working around CointOS itself.

**Project trees describe the product only.** Every role that writes a managed project's tree (managers, integrators, stewards, gardeners) writes it as if no agents built the product: spec, design, contracts, code facts, product defects and remaining product steps. CointOS workflow never appears there: no item or task names, decompositions, construction stages, roles, landings or gates, work reports, test packets, audits or retries. Workflow problems are CointOS defects, reported through `cointos attention` or a receipt and owned by this tree. `roles/_base.md` states the rule with an example.

- **Coin** is the Telegram control service. It reports and controls the daemon, manages projects, holds and revises queue items for the user, requests the canonical steward and launches explicitly scoped operators. It does not invent maintenance work.
- **Managers** perform one bounded decomposition or recomposition stage, keep the project plan's remaining product frontier honest, and propose children through `cointos queue`, pairing each behavior's test-contract item with an implementation item that depends on it. To change already-queued work, even started work, they `cointos hold` then `cointos revise` it; they never queue duplicates, and `cointos cancel` redundant work instead. Each worker brief carries a 5-20 word `Summary:` line for the dashboard, and a fresh session is shown the items its assignment already queued. Failed worker items automatically reach one manager pass, without magic report wording; managers may revise a false brief or replace oversized work while preserving unfinished work. They land their planning changes and finish with `cointos finish --complete|--blocked`; queued children continue independently.
- **The steward** is one low-reasoning system-wide roaming assignment. It spawns every `spawner.steward_every_seconds` times one plus the active or queued concerns (user-killed tasks excluded), once when managed projects have sat without work for `spawner.idle_steward_seconds` after work last settled, or on request. It inspects runtime state, configured projects and accessible trees, follows the strongest evidence and stops after one useful result. Knowledge-tree gardening is normal steward work: it may directly repair stale current truth, non-green leaves it can verify and dishonest plans. Outside knowledge trees it is read-only. When product work or managerial judgment is needed, it may submit exactly one attributed manager command with `cointos queue ... --kind command`; it cannot propose implementation kinds. It may instead perform one bounded registry action when enrollment itself is the concern. If the user must decide or act, it raises a daemon alert delivered by Coin. Its receipt carries its finding; a clean result is valid.
- **Test auditors** are medium-reasoning system-wide retrospective reviewers. After recent accepted product work, one samples a landing, compares tests with the owning specification, runs bounded suites, and checks whether plausible wrong implementations could still pass. A concrete semantic gap becomes at most one manager command in the owning project; it never edits product code, tests, plans or project knowledge itself. Its receipt carries its finding; a clean audit is valid.
- **Operators** carry one ad-hoc assignment with explicit standard, control or network abilities, started by the user (Coin or `cointos agent run`) or by any non-worker run (`cointos_operator`) for work with no route through the pipeline. A spawned operator gets no ability its spawner lacks, records `spawned_by`, and its required budget comes out of the spawning run's (`schema.spent`). Workers may not spawn: an operator would land their work unreviewed. A system operator's receipt states its result without changing product repositories; a project operator must leave clean merged work before a complete receipt.
- **Workers** carry one skeleton, test-contract, implementation or integration item on an isolated branch with one committed `.work-report.md`. A test writer's finish checks its tests against main: passing tests go to an integrator, failing ones are accepted as a hidden packet. An implementer's finish runs the hidden packet first and, on failure, keeps it working with only the failing tests shown. A revised item restarts them on its new brief with their branch intact. Tree/plan maintenance is left to the integrator.
- **Integrators** give one worker's code and its packet's tests, or tests already passing on main, a once-over against main and the contract, maintain the owning project tree (product facts only) and land through the daemon's gate, which runs the full suite. The verified landing, incorporation or return is their receipt; `finish --blocked` fails the item and routes its evidence to one bounded manager pass. An unresolved or exhausted manager escalates to the user. They may expose at most one same-project managerial follow-up.
- **Gardeners** provide free periodic maintenance across the CointOS source tree and every registered project's knowledge tree, verifying a small selected batch of leaves. **Tree auditors** (task kind `tree-audit`) inspect one structural concern across a representative sample. Both are bounded, mutually excluded per tree and finish with merged knowledge changes and a receipt stating any unresolved result.

The global default is low reasoning. `config/cointos.json` `reasoning` may name a default for test writing (`test-contract`) and for any role by name; test writers and managers default medium. Effort is pinned when a task is created, so a changed default reaches only later tasks, and explicit daemon-owned overrides win. Integrations use their role default without inheriting the worker's overrides. Per-reply reasoning limits and total run budgets are separate. Role class and GPU scheduling priority remain distinct.
