Qwen3.8 speed depends on the *effective live backend launch*, MTP speculation, prompt/context work, and concurrent occupancy—not just the model name or a saved recipe. Single-worker runs with MTP have previously decoded around 20–25 visible tokens/s; an MTP-less auto-load was observed around 9–10 tokens/s. Larger prompts and multiple concurrent requests can lower visible decode rate. These observations do not establish a universal throughput curve.

The historical MTP-loss mechanism was stale saved Lemonade options: a live managed launch had `--spec-type draft-mtp`, while the saved auto-load recipe lacked it and used `merge_args=false`, which resolved explicit desired llama arguments away. A 2026-09-20 options repair saved `ctx_size=262144`, `merge_args=true`, `--parallel 2`, and `--spec-type draft-mtp`; the exact Qwen3.8 managed-load payload also persists that recipe. The original actor that corrupted saved options is still unknown. Do not reload a healthy active model solely to investigate history.

On the 2026-09-26 two-worker CointOS-only probe, live Lemonade health showed Qwen3.8 launched with `--ctx-size 262144 --parallel 2 --spec-type draft-mtp`, and both occupied llama.cpp `/slots` entries reported `speculative: true`. Cumulative backend draft/accepted-token counters were nonzero. MTP was therefore enabled during the probe. David observed roughly 13 visible tokens/s aggregate across the two workers, versus roughly twice that for one worker. That comparative speed is David's observation, not an isolated controlled benchmark; the exact contribution of shared GPU/memory service, long-context prefill, MTP acceptance, and OpenCode/tool overhead has not been separated. After the two-worker pair completed, a single queued worker ran in this unchanged `--parallel 2` backend at David's observed roughly 13 visible tokens/s: `/slots` showed one processing slot with `speculative: true`, and host memory PSI remained zero. A prior single worker on the same two-slot MTP recipe reached roughly 21 token/s, so an idle second slot alone is not a proven explanation. Recent completed-request speculative counters imply lower draft acceptance than older cumulative totals, but the current request's acceptance is not isolated until it closes. Slot count is physical admission capacity, not a guarantee that using every slot maximizes batch throughput. `--parallel` is a llama-server startup option; the current documented slot API manages slot state, not live slot-count resizing, and Lemonade's llama.cpp backend allocates its KV buffer at model load. Changing the physical slot profile appears to require backend reload, so do not do it while a worker owns KV state. For overnight ingestion, measure completed useful work per hour and latency under one versus multiple concurrent requests before tuning a model-neutral adaptive scheduling policy. Primary references: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md?plain=1 and https://github.com/lemonade-sdk/lemonade/blob/main/docs/dev/backends-reference.md .

The current two 131072-token MTP sequences have passed idle memory and live two-request operation without pressure. Three full sequences had an unresolved model-load PSI emergency; four exceeded the configured GTT emergency threshold. The scheduler must derive lanes from selected route and live capacity facts, never embed Qwen3.8 or a permanent two-slot limit. Before changing capacity, inspect live `launch_command`, saved `recipe_options`, `/slots` speculation/occupancy, GTT, PSI, and per-request useful throughput, and preserve active workers.
