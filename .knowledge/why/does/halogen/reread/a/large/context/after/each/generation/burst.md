The experimental adapter's strict cache-loss guard treated a missing generation tail as loss of the entire prefix. Observed counters showed a 44,620-token prompt generating 64-token bursts, then `lost: engine retained 44620 of 44684 prefix tokens` and a switch restored from zero. The UI could remain at the original prompt's full read count while generated-tail recovery restarted reading. This is cache-state churn, not a collapse in raw decode speed.

Named KEEP states are limited to half the native KV pool. A 131072-position pool rejected long retained states once several contexts competed. Simply omitting KEEP avoids those pin refusals but a synthetic 40k/36k interleave still reread its 64-token generated tail, so automatic prompt caching alone does not establish complete tail retention.

The repair preserves/replays only a bounded missing tail up to scheduler.read_chunk_tokens, rather than declaring the whole context lost, and retains the completed generation tail with replaceable pins. Retire an old pin only after the next request has acquired its active region, then commit the replacement. The deployed 262144-position shared pool and 8192-token prefill workspace preserve the 131072-token per-request context. Interleaved 40k/36k synthetic contexts returned to their retained tails with one pending input token per 64 generated tokens, at approximately 63, 74 and 92 tok/s. This checks the repaired burst loop, not unlimited simultaneous context capacity.

Near-tail edits still cause large partial rereads. halogen_control.py pins only the end of each generation step (keep_end). Qwen3.8-Flash-Next's recurrent state cannot rewind, so when OpenCode re-sends the last assistant reply even slightly differently, that pin is useless. On 2026-11-17, divergence.common fell 12–300 tokens short of held. Halogen then resumes from its automatic prompt-cache snapshots (system_end, last_user_start, history_end; only about two 60 MB entries survive). Those can sit tens of thousands of tokens back: engine `kv pool` logs showed resumes from 51200, 69632, 61440, 74752 and 43008 rows of ~80–106k contexts. Compaction is a separate cause (how/to/monitor/halogen/cache/stability/in/cointos.md). The proposed fix is to also pin the prompt boundary at the start of each new client request, so a re-rendered reply rereads only that reply plus new input. Two things are unverified: whether two pins on one region double KV use, and whether a pin can be kept at the boundary alongside keep_end. Both need a native test with the daemon stopped, and deployment requires recreating the container.

Evidence is under ~/.local/state/halogen-trial/: cache-spawn-fix.log records the failed automatic-only alternative; cache-spawn-fix-v2.log and long-cache-retention-v2.json record the passing replacement check; near-tail-divergence.json records an earlier near-tail counterexample. stability-watch.jsonl holds numeric live evidence. Production probes use the CointOS gateway. Direct native lane tests require the daemon stopped and must restore it in finally. Actual session prompts must not be copied into diagnostic evidence.
