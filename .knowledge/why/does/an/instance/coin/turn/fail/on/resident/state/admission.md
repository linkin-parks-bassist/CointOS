The retired three-daemon deployment applied machine-wide admission policy independently. Each daemon subtracted the same loaded-model and desktop reserve, so secondary Coin instances could not admit their resident state even though they shared one runner. The supported deployment is now one daemon and one runner; what/are/the/cointel/identities.md owns it.

In that layout, lanes.switch waited for about 11.3 GB of native state headroom until timeouts.server_seconds, then raised MemoryError. The Telegram input remained pending without a reply. The 2026-11-15 fixture held read 2048 / prompt 11790, generated 0 for at least 45 seconds; the runner used 78% CPU, while a 16,859-token request through the default gateway completed in 67 seconds. This established an admission failure rather than a model/prompt-length failure. Lowering each reserve from 24 to 2 GB did not repair the duplicate accounting; a separate 19 GB Lemonade weight copy also consumed capacity. The rollback removed this topology.

One daemon can still lack physical headroom for an additional resident. Current source parks that thought as waiting_for=memory and releases the worker so admitted peers continue; it does not spend a server timeout blocking the lane or fail the turn for that wait. No reserve reduction or live-cache eviction is implied. how/does/cointos/protect/workstation/memory.md owns admission and its qualification limits.
