# Control-plane presence and live agent messaging

Status: fast-response slice implemented on `fix/snappy-initial-response` and awaiting
live deployment verification; introductions, stranger names, and the general live
message bus remain partially or wholly pending.

## Natural agent introductions

When Cointelprofessional refers to an agent by name, the first reference in each
outbound message should include that agent's current age and role in parentheses:
`Wren (6m, Steward)`. Later references to Wren in the same message should use only
the name.

- Treat each outbound Telegram message independently; do not assume an introduction
  in an earlier message still counts.
- For a live run, age means elapsed wall time since that run started. For a queued
  agent, use time since enqueue only if mentioning a queued agent is useful, and do
  not imply it has been running. Completed-agent notices should report the completed
  run's duration rather than time since completion.
- Round compactly to minutes or hours (`6m`, `2h`, or `2h 8m` when the extra
  precision matters). Derive this from durable timestamps, never invented prose.
- Use the actual assigned role, title-cased for presentation. Do not expose job IDs
  or raw lifecycle data unless David asks.

The presentation layer should own this rule so Telegram, dependent outbox results,
and status replies cannot drift into separate formatting conventions.

## Fast generated first responses

Move the useful initial Telegram response earlier again. It must be generated by
the capable resident control model with recent conversational context—not a canned
acknowledgement, JSON template, or deterministic intent-classifier phrase. It should
briefly answer or acknowledge the substance, then dispatch longer work only when
needed. Silence is preferable to repetitive boilerplate, except for the explicit
five-minute disaster fallback when the generated path has genuinely failed.

Measure time-to-first-generated-response separately from time-to-completed-work and
preserve one reserved control-plane request slot so worker load cannot starve it.

Implementation note, 2026-09-04: Telegram updates now become versioned durable turns
before inference. Resident GLM produces the bounded first response; up to two Qwen
deep-control processes claim turns outside polling and finish through typed publish-
or-silent tools; result presentation is also a separate service. Offline probes found
and corrected a GLM hallucination of Wren's completion time. Measured GLM response
latency after prompt correction was 0.25–0.58 seconds on three representative turns;
Qwen's deep silent decision took 18.0 seconds and an inspect-plus-answer turn took
12.2 seconds without blocking intake. See ADR 0005 and the control-flow tests. Live
Telegram deployment remains the acceptance gate. Two attempted independent local
reviews were not counted as verification: Sieve (Qwen Verifier) and Ternary (GLM
Verifier) both hit their inference timeouts without verdicts. A subsequent direct
state-machine review added boot/process identities, a ten-minute whole-turn deadline,
and idempotent replay for task amendments as well as creation.

After service deployment, a contention probe ran while Coder-30B was already serving
an ecosystem agent and Qwen was simultaneously making a deep terminal decision. GLM
returned the truthful first response in 2.15 seconds; Qwen finished silently in 6.15
seconds. This demonstrates model/process separation under representative load, not
yet an end-to-end Telegram delivery measurement.

## Significantly stranger generated names

Raise the frequency and breadth of odd and mildly alien generated names
substantially above the current conservative policy. Names should remain
task-sensitive, pronounceable enough to discuss, internationally broad, and funny
or strange without fantasy sludge, mascot energy, cultural caricature, or forced
quirkiness. `Journathan` remains the tonal reference: a dry linguistic accident is
better than a list of stock eccentric names. Keep generation model-driven rather
than using a fixed pool, and evaluate repetition and blandness across recent names.

## Live inter-agent message bus

Add a durable, bidirectional message bus behind a transport-agnostic interface. Any
specific live agent must be able to message any other specific live agent directly;
this is not a privileged control-plane-only inbox. It must also support:

- direct addressing of one exact live run;
- role-local announcements to every live agent currently assigned a given role;
- global announcements to every live agent in the ecosystem;
- an explicit control-plane address for useful findings, questions, and relays to
  David.

Direct messages and announcements should become visible immediately during a live
run, not merely be appended to the next invocation's starting prompt. The runner
should maintain a low-latency inbox and inject pending messages at the earliest safe
model/tool boundary. If an adapter cannot interrupt an in-flight model request, it
must expose that limitation truthfully, queue the message durably, and deliver it as
soon as that request returns. Longer-term inference adapters should support genuine
mid-run interruption or cooperative yields so urgent messages do not wait behind a
long generation.

Required initial message kinds are:

- `information`: new context or a correction;
- `request_status`: return a concise progress/checkpoint report;
- `wrap_up`: stop expanding scope, preserve useful work, and finish promptly;
- `cancel`: checkpoint and terminate truthfully under explicit authority;
- `handoff`: send a bounded question or result to another named live agent;
- `announcement`: publish relevant context to a role or the whole ecosystem.

Messages need sender, address kind and target, recipient run identities resolved at
publish time, creation time, priority, delivery/acknowledgment state, and payload,
stored durably without leaking Telegram or professional content into Git. Delivery
must be idempotent per recipient. Acknowledgment means the target observed the
message, not that it obeyed or succeeded. Record causal links in the audit log.
Bound announcement fan-out and retention explicitly; broadcasts convey information
and must not silently clone work or create reply storms.

The implementation must not depend on OpenCode, Telegram, Lemonade, systemd, or one
particular model server. Those are adapters around the shared mailbox and lifecycle
representation. Do not fake live messaging by mutating the original prompt.

Safe shutdown should use this channel first: pause intake, send `wrap_up` to each
live agent, wait a bounded interval for acknowledgment and a durable checkpoint,
then escalate according to explicit lifecycle policy. Interrupted runs must become
recoverable or truthfully failed; they must never remain dead records labelled
`running`.

Suggested acceptance tests cover messages during inference and tool use, duplicate
delivery, target completion before delivery, crashed senders/recipients, reboot,
wrap-up timeout, authorization boundaries, and multiple simultaneous agents.

— Palinode (Codex agent), 2026-09-04
